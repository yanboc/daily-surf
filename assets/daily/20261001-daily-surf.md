1. **[RefCon: Iterative Refinement and Contrastive Memory Extraction for Context-Evolving Agent](https://arxiv.org/abs/2609.39143)**
   - 元信息：2026-09-30（arxiv abs；v1 submitted 2026-09-30；cs.AI / cs.LG / cs.MA）；预印本；主题标签：Agent Memory / Context-Evolving / MaTTS 记忆抽取 / RefCon·DivCon / AppWorld·BFCL；分级：S
   - 核心问题：长程 Agent 轨迹里有可复用经验，但无金标时单轨迹抽取易把「看起来合理却失败」的步骤写进记忆；并行多样与顺序自精炼通常分开做，缺少同时抬质量与对比信号的抽取器。
   - 机制/设计：RefCon 在测试时学习（TTL）流中：对任务 \(q_i\) 先用检索改写后的记忆 \(m_i\) 生成 \(\tau_{i,1}\)，再经自精炼得 \(\{\tau_{i,n}\}_{n=1}^{N}\)；记忆抽取器对整组轨迹做自对比，蒸馏候选记忆 \(m_{\mathrm{new}}\)（含 when-to-use 索引与 content）；再按嵌入相似度 \(\epsilon\) 做库内/库间去重写入 \(\mathcal{M}_{i+1}\)。检索侧用 retrieve–rerank–rewrite；管理侧按检索次数 \(f\) 与成功贡献效用 \(u\)，当 \(f\geq\alpha\) 且 \(u/f\leq\beta\) 时删除。变体 DivCon 把精炼换成显式多样性探索。主骨干 GLM-4.6 + text-embedding-3-small；默认 scaling \(N=3\)（DivCon 为 2）。评测：AppWorld（dev；TGC/SGC、Avg@3/Pass@3）、BFCL-V3 multi-turn travel（50 题）、SWE-bench Verified Mini。
   - 证据：无金标设定下，RefCon 在 AppWorld Avg@3 TGC/SGC 达 74.30/52.67，BFCL Pass@3 82.00，优于 ACE/ReasoningBank 等无标基线，并接近部分有 GT 方法。接入各框架后相对无 scaling：ACE +21.6%、ReMe +16.6%；DivCon 在 ReasoningBank 上 +35.5%。SWE Mini 第 3 轮 RefCon 60.00，超过 ACE(w/ GT) 与 ReMe(Seq)。相对顺序 scaling 仅多约 0.17M–1.18M token（≤3%）。Scaling：\(k=1\to5\) 时 RefCon 升至 76.0%，DivCon 约 71% 平台。失败案例：BFCL 上自精炼可破坏已正确轨迹；AppWorld 无 scaling 的 ACE/RB 可低于 ReAct；ReMe 并行仅在轨迹分数不同时才对比，信号常缺席。
   - 局限：Limitations——虽测 GLM-4.6 / Gemma 4 31B / Qwen3.5 9B，跨架构与调优风格泛化未保证；scaling 仅到 \(k\leq5\)，更大预算是否饱和未知。主域为 AppWorld/工具调用，非企业审计日志。失败条件：窄分布工具调用上只做自精炼、不做对比；或单轨迹无标抽取把静默 API 误用（如 `show_song_privates` 无 `play_count`）固化成「成功经验」。
   - 对办公 Agent 或 Agent 基础设施的意义：直接落在 AppWorld 类多应用工具链——生产记忆写闸应默认「多轨迹精炼 + 成败对比」再入库，而不是一次 rollout 摘要。可把「同场景后续任务是否变快」与效用删除阈值做成回归门，并在邮件/通讯录类任务上专门检查「跳过 API 探查」类坏记忆。

2. **[Context Language Models](https://arxiv.org/abs/2609.37725)**
   - 元信息：2026-09-29（arxiv abs；v1 submitted 2026-09-29；cs.AI / cs.CL / cs.LG；Meta Superintelligence Labs 等；代码 facebookresearch/context-language-models）；预印本；主题标签：Context Engineering / 上下文即文件 / 多 Agent 上下文并存 / Suffix Cache Reuse / ContextBench；分级：S
   - 核心问题：上下文是 Agent 的核心状态，但管理权长期在 harness（阈值压缩/固定工具动作）上；模型只能追加 token，难以在中途外科式编辑、跨 Agent 维护计分板，长跑成本与注意力稀释随之失控。
   - 机制/设计：形式上将 \(c_{t+1}=c_t\oplus f^{\mathrm{LM}}(c_t)\) 推广为 \(c_{t+1}=f^{\mathrm{CLM}}_\theta(c_t)\)。实现：把 live context 镜像为可 Bash 编辑的文件，改动同步回下一轮 prompt；不改则默认追加。多 Agent：多上下文文件并存并可创建/删除子 Agent 文件。诊断套件 ContextBench（Needle Retention / Sudoku Sketchpad / KV Store / Log Triage）隔离「管上下文」能力。学习：自然语言指令或 skill 演化环；训练用 stepwise GRPO + 成功门控的效率优势（在成功轨迹子集内奖低 FLOPs）。服务：定义 prefix-reuse FLOPs；Suffix Cache Reuse（SCR）在中途编辑后复用存活后缀 KV（\(K=6\)）。
   - 证据：Qwen3.6-27B、32K：BrowseComp-Plus Acc 59.4%，相对最强 Codex 式摘要 +11.4%，prefix-reuse FLOPs −21.5%；TB2.1 匹配最强基线且 FLOPs 约 70%；TBLite 73.7 vs 67.0。EdgeBench-10（12h）：CLM 44.6 @ 179 PFLOPs vs 摘要 42.3 @ 437（约 −59% FLOPs）；Claude 4.6 Sonnet 上 CLM 51.0 vs 摘要 42.3。Software World（6 Agent、24h、272K）：同算力下下游加速相对摘要 swarm 再高 65%。RL：Qwen3.5-9B BrowseComp-Plus 28.8→42.5%，FLOPs 1.52→1.34，对齐训后摘要且更省。SCR 相对标准 SGLang 服务侧约 −35%（匹配性能）。技能演化在 ContextBench KV Store 上最高可 +35.9 分。
   - 局限：Discussion——可编辑上下文成为注入/自写持久指令的新通道（文内引用 compaction 自插未授权指令案例）。SCR 复用的是编辑前缓存态，属近似；评测主面为 coding/deep research/仓库优化，非邮件日历写闸。失败条件：把「模型可自由改上下文」当成已治理 harness；或在未加完整性护栏时把 CLM 当默认办公长跑栈。
   - 对办公 Agent 或 Agent 基础设施的意义：把上下文管理从固定 compaction 合同改成「模型可维护的工作记忆文件」，并自然支持多 Agent 共享工作区计分板。生产可先用指令/skill 钉策略（何时压、压前备份），再用 SCR 降成本；写动作与权限仍须外置闸，不可假设 CLM 自管上下文即安全。

3. **[CollabFlow: Recursive Self-Improvement of Agent Collaboration](https://arxiv.org/abs/2609.38662)**
   - 元信息：2026-09-29（arxiv abs；v1 submitted 2026-09-29；cs.MA / cs.AI；Oct 1 recent listings）；预印本；主题标签：Multi-Agent / 证据条件通信 / Collab-Director·CTB / 单写者 Executor / 递归自改进；分级：A
   - 核心问题：多 Agent 协同的「自改进环」常断在三处：协作预定义在算子/角色层；只学拓扑却 verbatim 传消息扩散错误；对自身结果做奖励最大化会塌缩到少数团队，后续轮可学多样性不足。
   - 机制/设计：可训 Collab-Director 构造完整 Agent 协作图 \(G=(V,E,o)\)，边协议 \(\in\{\mathrm{FinalOnly},\mathrm{OneWay},\mathrm{Interactive}\}\)；冻结执行器跑图，本轮结果回训 director。边上 Evidence-Conditioned Communication：证据分 \(\ell\in\{0,1,2\}\)（通过可执行检查=2、检索支持=1），\(\Delta=\ell_i-\ell_j\) 与边际 \(\kappa=1\)——强则采用、弱则保留、否则一次无工具有界修订；有状态任务仅一个 Executor 持写权限。跨轮用 Collaborative Trajectory Balance（CTB）对规范团队一次计分，目标为奖励比例分布，并给出自生成目标轮间 TV 上界随记录累积收缩。评测 12 数据集（IID：HotpotQA/TriviaQA/AIME 2026/MedXpertQA/ALFWorld/MBPP+；OOD：MuSiQue/NQ/MATH-Hard/GPQA/HumanEval/WebShop），Director 与冻结执行器均为 Qwen3.5-9B，同预算。
   - 证据：IID Avg EM 75.94（相对直接骨干 +18.0）、OOD Avg EM 69.92（+36.6）；平均领先最强基线约 +2.27 EM / +4.37 Acc（五跑，\(p<10^{-2}\)）。去掉通信或 director 训练掉点最大；证据门/强制 OneWay/处处修订在 OOD 惩罚更大（约 14–16 点）。CTB 相对 GRPO/PPO 团队分布更稳，成功路径 26 vs ≤15。另六冻结执行器均受益，弱骨干增益更大（IID Pearson \(r=-0.96\)）。每条 token 成本最低。
   - 局限：Appendix I——属有界 RSI：评估器、执行器、Agent 种群与更新规则固定；单写者不保证计划正确/观测新鲜/对外一致性；证据规则可被不完整或误导性真证据带偏；稀疏非平稳可靠性未必校准。评测非办公连接器写闸。失败条件：拓扑已学却仍 verbatim 采纳；或无证据门时把并发写交给多 Executor。
   - 对办公 Agent 或 Agent 基础设施的意义：给「评审/调研/写回」多角色流水线一条可验收合同——边上传的是带 provenance 的证据分，写权限钉在单一 Executor，编排策略用 CTB 保团队多样性而非塌缩到一种 SOP。生产可把「采纳须证据边际」与「顾问只读、执行者可写」挂进多 Agent 办公编排，并对 OOD 任务回归证据门消融。
