1. **[A Benchmark and Diagnostic Study of Epistemic Admission in Shared Agent Memory](https://arxiv.org/abs/2609.30813)**
   - 元信息：2026-09-28（arxiv new listings；v1 submitted 2026-09-25）；预印本；主题标签：Agent Memory / 共享记忆准入 / 相关推广与谱系坍缩 / Mem0·A-MemGuard / 写回环；分级：S
   - 核心问题：共享记忆与单 Agent 记忆不同——Agent 把检索到的信念复述/改写后写入，会把「重复」当成「独立证据」，虚假多数随之放大；且假信念一旦准入，后续读者代价随团队规模增长。现有评测很少固定冲突/不等可靠证据，也很少在运行系统里同时观测准入→检索→再写入。
   - 机制/设计：Correlated Promotion Benchmark（CPB）。准入策略 π 对候选 m 与证据图 Em 输出 PROMOTE / REQUEST EVIDENCE / KEEP PRIVATE / ABSTAIN，仅 PROMOTE 改共享库。**(1) CPB-Static**：从 claim-verification / FEVER、多跳编辑、维基引用图等公开标注源组装 1,200 个六 Agent 情节（训/验/测 600/200/400），金规则要求谱系坍缩后 ≥2 独立源才 promote。**(2) CPB-Live**：六 Agent × 六轮、每骨干 100 配置（相关同意、并发冲突、混合、双源 verbatim/改写/权威类型等）；场景事先固定谱系；另设只读 consumer 在第 6 轮仅凭库作答。策略含 share-all、多数票、独立性票（近重复坍缩后需两组支持）、DEPEN、GovMem 相关审查、**源类型治理门**、LLM judge，以及 Mem0 写路径与 A-MemGuard 一致性检查。主骨干 Qwen3.5-9B，复现 Gemma-3-12B、Llama-3.1-8B、Claude Opus 5。
   - 证据：Live 上仅治理门在仍作答时把 damage 压到 share-all 的 0.112–0.152，假采纳 0.06–0.09、正确率 0.58–0.65；独立性类 FA 0.119–0.306 却 TA 更低（0.051–0.127），宁可拒真。Mem0 在 share-all 下 damage≈1.0，去重多把假候选折进已有假信念；A-MemGuard 对假候选拒绝率约 0.00–0.18。无竞争真信念时，consumer 在 0.97–0.99 探针中断言唯一可见假信念（553 探针）；有竞争真时假-only 降至 0.15/160。改写可过表面坍缩（采纳约 0.65–0.72）；把改写标成权威登记文档后治理门采纳升至 0.70。关掉 Agent 对共享库的检索后，封闭族声明依赖从 189→0、候选/配置 8.3→2.2，但假写入几乎不变——写回主要加同意而非新假源。
   - 局限：Appendix S——Live 全为作者虚构以便固定谱系与真值，不估计部署发生率；相关同意族的父独立性由「不同引用」假定；竞争真的保护只在并发冲突族测得；库有 contest/demote/supersede 但对比策略未用；断言 grader 与 judge 均为 LLM（各 120 项双人校验）；Live 为预注册描述统计、无假设检验。失败条件：把「去重/一致性检查」当准入治理；或无源谱系时用多数票/权威标签给改写假信念放行。
   - 对办公 Agent 或 Agent 基础设施的意义：企业共享记忆（CRM 结论、制度问答、跨角色交接）的写入闸必须把「谁说的、是否独立」从文本相似度里拆出来——生产可对写入强制声明源类型/租户证据等级，并在写闸前禁用以库养库的自引复述；否则假 SLA/假承诺一旦入库，下游几乎必然当事实复述。

2. **[HasMem: Hard-Origin Adaptively Softened Memory for Long-Term LLM Agents](https://arxiv.org/abs/2609.30797)**
   - 元信息：2026-09-28（arxiv new listings；v1 submitted 2026-09-25）；预印本；主题标签：Agent Memory / Context Engineering / 连续软记忆宽度 / 硬原点等价 / Reader·Global 读出；分级：S
   - 核心问题：文本记忆与上下文压缩能复用历史，但把连续记忆槽「改宽/改窄」会直接改变冻结 LLM 的输入，使容量分配与读出耦合；需要在可验证的硬 prompt 原点上做逐步软化，而不是一上来就不可审计的连续压缩。
   - 机制/设计：HasMem 在冻结骨干 \(W_0\) 外维护 Soft Bank 与跨步 Global。每条记录从冻结 token 嵌入初始化（硬原点）；Controller 选 KEEP/SHRINK/EXPAND；Writer 仅在宽度变化时重编码；Reader 做低秩读出适配；GRU Global 条件化重编码与读出。全 KEEP 轨迹在相同检索与输入构造下与硬 prompt 等价。训练：\(W_0\) 冻结，用 MSC 训练 split 的 QA 监督 + 位置成本与 damage hinge；策略阶段用有界搜索找可降位置且不伤 NLL 的 SHRINK 序列。评测更新在见问题前完成（历史驱动维护）。
   - 证据：主配置冻结 Qwen2.5-7B、\(k=8\)。MSC-derived 重建探针（dev：268 owners / 535 问，至多 7 条/owner）：相对硬参考，F1 95.3 vs 90.9（+4.4pp），EM 84.3 vs 88.1（−3.7pp），帧位置比 \(R_{\mathrm{all}}=0.936\)。在近匹配每问 body 预算下，六配置均值保留约 0.83–0.91 时，学得重编码相对规则重编码 EM +8.0–23.6pp。固定参数与规则目标 \(\rho=0.75\) 时，Global 读出 EM +2.24pp（owner 级精确配对，Bonferroni 八比较 \(p=0.0146\)）。LongMemEval-S 全 500 问：局部 F1 3.4→8.9，answer NLL 12.257→5.274，但 EM/Brief 下降。消融：去掉 Writer hinge → 全 KEEP、退回硬参考；主轨迹 1470 KEEP / 516 SHRINK / 0 EXPAND。
   - 局限：Limitations——MSC-derived 为开发集句级重建、每 owner ≤7 条、规则天花板 100.0，需更长史与独立测试集看累积/干扰；F1 升常伴随更少 UNKNOWN、更低 EM、更高 NLL；Table 4 有离散位置残差与维护时序混淆；存储/延迟还依赖精度与实现；Gaussian-input 与 rule-action 部署未测；本地 LongMemEval judge 待对照官方配置。失败条件：把更高 F1 当成更忠实回忆（EM 已降）；或在关键事实尚未外置时过度 SHRINK。
   - 对办公 Agent 或 Agent 基础设施的意义：给「会话笔记/客户偏好槽」一条可审计压缩路径——从硬原文嵌入起步、按槽学宽度，而不是一次性摘要毁掉可核对原点；生产可把 KEEP 等价当作回归门，并把「决议是否已写入工单/表格」当作可 SHRINK 的前置条件。

3. **[AgentWorld: Benchmarking Long-Horizon Collaboration of Multi-agent LLMs](https://arxiv.org/abs/2609.31590)**
   - 元信息：2026-09-28（arxiv new listings / cs.MA；v1 submitted 2026-09-25；标为 COLM 2026）；预印本；主题标签：Multi-Agent / 长程黑盒协同 / 通信失效 / Causal Collaboration Effectiveness / 非对称角色；分级：A
   - 核心问题：既有多 Agent 榜多为短交互（<20 步）、竞争设定或把个体分加总，难以隔离「真协同」；需要长地平线、信息不对称、必须靠自然语言协调的评测，并区分「做成了」与「哪些动作因果上帮了忙」。
   - 机制/设计：基于 Kaetram MMORPG 沙箱的 AgentWorld：1056×768 世界、13 个高层工具（move/attack/harvest/craft/transfer/chat 等），回合制黑盒——Agent 看不见同伴内部状态/观测/动作史，只能 chat。100 个人工标注任务 + 100 增强变体；每任务 3–20 名非对称角色、约 25–55+ 轮、不可单人独解。指标：确定性 Python 判分的 SR、分目标 PSR，以及 **CCE**（LLM 对动作做二元因果贡献判断 → 反向构 Causal Action Graph，失败任务 CCE=0）。主评 Gemini 3 Flash / Claude Haiku 4.5 / GPT-5 Mini / DeepSeek R1-70B；基线含 random、单 Agent、无通信、共享计划但无通信、oracle 通信。
   - 证据：主集 SR：Gemini 52.0%、Claude 45.0%、GPT-5 Mini 36.0%、DeepSeek 20.0%；PSR 更高（Gemini 71.5%）；CCE 最佳仅 0.320（成功时 Claude 条件效率 0.653 > Gemini 0.609）。通信量≠成功：GPT-5 Mini 均 44.1 条消息却排第三，失败任务聊天占动作 26%；DeepSeek 均 7.5 条且首聊约第 5 轮。基线（Gemini）：random 5.7%、共享计划无通信 17.6%、无通信 22.9%、单 Agent 28.6%、vanilla 52.0%、oracle 通信 60.0%（仍余 40% 失败）。增强集全面掉分（Gemini 52→24%）。通信错误聚类中 stale/redundant 占 37.7%。CCE 与人标 84 项 κ=0.64；换裁判模型排序稳定。
   - 局限：正文无独立 Limitations；场景为游戏沙箱而非办公工作流；CCE 依赖 LLM 因果判断（虽有人机一致性，且包容标注使 CCE 偏上界）；三跑方差分析仅 Gemini×35 任务子集。失败条件：用消息条数或 PSR 替代协同质量；或假设「共享一份计划就够」却关掉执行期通信（SR 17.6%）。
   - 对办公 Agent 或 Agent 基础设施的意义：虽是 RPG，机制直接映射「多角色、长流程、只靠消息对齐」的办公编排——要测的是早期协调窗口、执行期可修订共享计划、以及抑制陈旧/冗余状态广播；生产上可为多 Agent 项目加 CCE 类因果审计，并警惕「多开会少干活」的通信过载。

   - 局限：本窗仅 Python AG-UI 路径，包版本 tag 尚未包含该提交；不内置邮件/日历/Office 连接器语义；自定义命名空间仍依赖宿主正确挂载 `ToolApprovalMiddleware`——未配置则无额外保护面。失败条件：把客户端可写 Shared State 当成审批规则源；或构造期读死 `source_id`、运行期改名后未再纳入保护集（本 PR 刻意按 live middleware 发现）。
   - 对办公 Agent 或 Agent 基础设施的意义：补上 HITL 的另一半——**批准权威既在会话 pending，也在服务器拥有的状态命名空间**。凡经 AG-UI 挂 GenOffice/Workspace/Graph 写工具，生产必须把自定义审批 `source_id` 列入 Shared State 保护键，并回归「客户端清空 rules ≠ 自动放行」。

1. **[What is an autopilot in Microsoft Foundry?](https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/autopilot-overview)**（底层配套：[Microsoft Agent 365 integration with Foundry](https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/agent-365-integration)、[Grant agents access to Microsoft 365 resources](https://learn.microsoft.com/en-us/entra/agent-id/grant-agent-access-microsoft-365)、[Microsoft Entra Agent ID design patterns](https://learn.microsoft.com/en-us/entra/agent-id/concept-agent-id-design-patterns)、[Governing Agent Identities](https://learn.microsoft.com/en-us/entra/id-governance/agent-id-governance-overview)；产品窗口：[Introducing the new Copilot with Home, Code and Autopilot](https://blogs.microsoft.com/blog/2026/09/25/introducing-the-new-copilot-with-home-code-and-autopilot/)）
   - 元信息：2026-09-25 产品公告明确 Autopilot「月末 private preview」；窗口内（2026-09-26～28）对应落地准备；已发布（Microsoft Learn 工程文档 + Official Blog）；主题标签：办公 Agent / 独立邮箱·日历·Teams / Agent user 身份 / Agent 365 注册与审计 / 人机赞助人治理；分级：S；重复出现，值得关注
   - 核心问题：常驻办公 Agent 若只能「代登录用户」发信/改日历，则无用户回路时无法动作，群聊里又会错挂权限与归因。需要把「谁在行动」钉成目录级主体，并把 Outlook/Teams/文档写路径挂在可审计身份与访问包上，而不是共享服务账号。
   - 机制/设计：Foundry 用身份而非能力清单定义 Autopilot——**agent identity（服务主体）+ agent user account（用户对象）** 同时存在才是 Autopilot；后者提供邮箱、日历、OneDrive、Teams 在场与组织架构席位，使 Agent「作为自己」在群聊与事件触发场景动作。三类对照：Assistive（代用户）、Background service（应用权限、无 M365 用户面）、Autopilot（数字同事）。Blueprint 只定义工具能力与平台基础设施，**不授予具体团队业务资源**；实例由经理决定可触达的项目/站点（「有 SharePoint 工具 ≠ 有任一站点」）。Agent 365：发布后进 Registry，管理员审批后可在 Teams 等表面「雇佣」实例；Hosted agent 才支持 Autopilot 发布。Entra 通道权限表把邮箱/文件评论/Teams 聊与频道的入站/出站拆成独立 Graph 范围（如 `Mail.Read`/`Mail.Send`、`ChannelMessage.Send`）。治理：访问包 + 赞助人审批与到期；赞助人离职转交经理；Conditional Access / ID Protection 可挂 blueprint。
   - 证据：Autopilot 概览写明无用户回路与群聊代操两种失败模式及 agent user 解法；Agent 365 集成表区分 Prompt/Hosted 对 Registry、Autopilot 发布、活动采集的支持；Grant M365 文给出按通道的入站/出站权限矩阵与委托 vs 应用权限取舍；设计模式把 Digital worker 钉为 blueprint→identity→**1:1 agent user**；治理概览写明 Agent 自请/赞助人代请/管理员直配三条访问包路径。产品文承诺供应商评审全流程（排期、会前、会议、跟进）与 Today（邮件/日历/Teams）指挥面。
   - 局限：主工程文档偏契约与身份模型，缺发信/改日历的逐工具 HITL schema、误操作率或审计字段样例；Autopilot/Agent 365 依赖 Frontier 与许可，非 GA 实测；数据驻留上 Foundry（Azure 区域）与 Agent 365（Entra 租户地理）不同，合规租户须显式配置采集。失败条件：把「有独立身份」当成已具备写动作人审；或 blueprint 工具面过宽却未做实例级站点/邮箱授权与访问包过期。
   - 对办公 Agent 或 Agent 基础设施的意义：把「改真文档 + 会务跟进 + 邮件/日历」绑到租户级 Agent 身份——生产应给常驻办公 Agent 独立 Entra agent user/赞助人与访问包到期，并把 Outlook/Teams 写路径挂在可审计主体与 Purview/条件访问闸上，而不是复用员工个人 OAuth 长效令牌。

2. **[Trigger workspace agent runs](https://developers.openai.com/workspace-agents/trigger-runs)**（配套：[Authenticate with Workspace Agent access tokens](https://developers.openai.com/workspace-agents/authentication)、[Trigger a Workspace Agent from the API](https://developers.openai.com/cookbook/examples/chatgpt/workspace_agents/workspace-agents-api-trigger)、[ChatGPT Workspace Agents for Enterprise and Business](https://help.openai.com/en/articles/20001143-chatgpt-workspace-agents-for-enterprise-and-business)）
   - 元信息：官方开发者文档与 cookbook（cookbook 标注 2026-06-18；Help Center 近窗持续更新）；已发布（OpenAI Developers / Help Center）；主题标签：办公 Agent / API 触发跨系统工作流 / 邮件线程 conversation_key / 写动作人审 / 运行态可靠性；分级：S
   - 核心问题：会议跟进、采购审批、客诉升级等办公流常由工单/邮件/CRM 在 ChatGPT 外启动；若只能 UI 点跑，则无法嵌入现有系统，且异步跑完后编排侧看不见排队/挂起/失败。需要「外部事件触发已发布 Agent」的合同，并把审批与应用权限留在 Agent 配置里。
   - 机制/设计：`POST /v1/workspace_agents/{agtch_…}/trigger` 用 Workspace Agent access token；体字段 `input`（必填）与可选 `conversation_key`（跨多次触发续同一会话，文档示例为 `email_thread_abc`）。`Idempotency-Key` 保证同事件重试不二次入队。默认响应 `202` + `conversation_url`，**不返回完成正文**。可靠性增量：请求头 `OpenAI-Beta: workspace_agent_runs=v1` 后返回 `agent_trigger_run_id`（`apirun_…`），可轮询至 `queued`/`in_progress`/`suspended`/`completed`/`failed`；`suspended` 表示等待外部动作或工具（与写闸人审对齐）。Cookbook 强调：API 只启动；指令决定目的地与是否先问；应用设置决定能否写与是否 Always ask；敏感写应保持审批，低风险写才可自动。Help Center：apps/connectors 写默认 Always ask；Connector Action Constraints 可再收窄收件域/文档范围；共享连接优先 Agent-owned 服务账号。
   - 证据：trigger-runs 全文给出端点、字段表、beta 轮询契约与错误码（401/403/404/409）；cookbook 给出从指令草稿→API channel→幂等触发→在目的地核验的端到端步骤，并明示「触发成功但无写入时查 Agent 配置而非 HTTP」；Help Center 写明写闸默认、域/文档约束与 Slack/API 办公场景。
   - 局限：无 beta 头时仍无 run ID/响应体，编排只能靠目的地侧核验；约束只管请求形状不管回传内容；无公开误拦/漏拦率。失败条件：把 `202` 当业务成功；或 API 触发路径上把写闸改 Never ask 却无域/文档约束与幂等键。
   - 对办公 Agent 或 Agent 基础设施的意义：给出「邮件线程/工单事件 → 已治理 Agent → 人审后写回」的可复制集成面——`conversation_key` 钉线程、`suspended` 对接审批、`Idempotency-Key` 防重发；生产上把 schedule/API 触发与写闸、服务账号连接放进同一发布检查清单。

3. **[Claude Tag now supports personal connectors in channels](https://claude.com/blog/claude-tag-now-supports-personal-connectors-in-channels)**（底层：[How agent identity works](https://claude.com/docs/claude-tag/concepts/agent-identity)、[Work with Claude Tag](https://claude.com/docs/claude-tag/overview)）

   - 核心问题：频道里的办公协同常要「看我的日历空档 / 我的 Drive 计划 / 我名下的 CRM 单」，但若只能挂管理员配的共享连接器，要么把个人数据暴露给整频道，要么 Agent 够不着。需要在共享频道里按人启用个人连接器，并保留发帖前的人审与无人值守边界。
   - 机制/设计：频道会话默认走 **Admin 配置的 Access bundle + 服务账号**（审计归服务主体）；个人任务经用户同意后，才用其 claude.ai 连接器（日历/Drive/CRM 等），且**仅该用户可触发**，同频道他人不能代用。输出：手动 review 每条再发帖，或 auto 模式（敏感内容仍拦下待审）；Enterprise 将可强制全员 review。无人值守（定时、自启动）**仍只用频道共享连接器**——on-call 等应配共享 runbook/监控，而非依赖个人连接器。身份文档补全：沙箱内不落凭证；出站经 Agent Proxy 按连接规则/域名/环境网络层放行并在边界注入凭据；个人连接器工作记在用户名下，频道工作记在服务账号下。
   - 证据：博文完整叙事（Priya 在 `#checkout-migration` 用频道 GitHub + 个人 Drive 对照已合并 PR 与计划）；明确 auto/review 与「个人连接器不跑无人值守」；agent-identity 文给出频道 vs DM 四维对照表、Proxy 三层放行与「他人帖子当信息、本人指令当控制」的设计。Team 滚动、Enterprise 随后。
   - 局限：属产品/工程说明非对照评测，无误发率或敏感分类准确率；Enterprise 强制 review 仍为「将可」；帖子一旦发出全频道可见，个人连接器不解决「频道广播面」。失败条件：把 RFP/定价等敏感草稿频道建为「仅个人连接器」却开 auto 发帖；或期望定时任务走个人日历/CRM。
   - 对办公 Agent 或 Agent 基础设施的意义：给出「共享协作面 + 个人数据面」分离配方——频道服务账号做可审计共享工具，个人连接器做人审后的按人取数；可与 Entra agent user / Workspace Agents 写闸对照：一边解决频道归因与个人授权，一边仍须对不可逆发帖/发信做人审与无人值守边界。
