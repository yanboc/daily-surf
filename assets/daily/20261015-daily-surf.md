1. **[Reliable Memory from Unstable Growth: Curating Self-Written Agent Playbooks with Randomized Experiments](https://arxiv.org/abs/2610.18427)**
   - 元信息：2026-10-13（abs：Submitted on 13 Oct 2026；cs.CL；南洋理工 / VinUniversity；代码 anonymous.4open.science/r/rbc）；预印本；主题标签：Agent Memory / 自写 playbook 不稳·RBC 随机区块策展 / ACE·Dynamic Cheatsheet·AppWorld·WebShop·ALFWorld；分级：S
   - 核心问题：ACE、Dynamic Cheatsheet 等把经验写成可进 prompt 的 playbook，但「写什么」与「留什么」仍由同一 agent 自判。同流程不同生长 run 可把 playbook 从大幅增益翻成相对无 playbook 低至 **69.6** 分；自贴 helpful/harmful 标签也拦不住伤害块。能否用**可测的任务成功差**而非模型自评来决定服务哪些教训？
   - 机制/设计：**Randomized Block Curation (RBC)**，只替换 judge/serve，不改生长。(1) 用 all-mpnet + Ward 把教训聚成 \(m=8\) 块；(2) 在 practice 任务上对每块独立 Bernoulli(\(1/2\)) 纳入/排除，岭回归估计块效应 \(\hat\theta_j\)（Banzhaf 平均增益）；(3) 按 \(\hat\theta_j>0\) 贪心装入 token 预算 \(B\)（主设 40% whole）；(4) 生长 \(K=3\) 本 playbook，在新鲜 practice 上于「策展集 / whole / 空」共 \(2K+1\) 候选中选 \(\hat S\)。骨干 Qwen3.8-27B / Qwen3.5-9B / Gemma-4-31B；AppWorld 区分 pass/fail 与 per-test 反馈。
   - 证据：19 设定均值成功——RBC **66.9** vs Whole **55.5** / No playbook **54.1** / Own 自判 **53.8** / Best-Full（只选整本）**66.4**。ACE 上 RBC 相对无 playbook 最大掉点仅 **0.8**（Whole 达 69.6；各基线至少 5.4）。ACE tags 与实测块效应秩相关仅 **0.21**；长生长（至 10 pass）时 Whole 在 27B AppWorld per-test 可落到 46.6（无 playbook 78.4），RBC 仍到 **84.9**。消融：只策展或只选型各约 61.9/62.2，两者合用三 run 到 67.2。
   - 局限：正文 Limitations——仅两记忆系统、三基准、三开源模型；块效应可加时策展最优，整本重写（DC）时常退回选 whole；需多本生长 + practice 可观成功；常数在 4 个 ACE 设定上固定；playbook 生长后固定，在线边长边服务未覆盖。失败条件：只用 agent 自贴标签裁剪却宣称已控伤害；或只比整本记忆、不测块级随机对照；或 practice 与评测分布错位仍信选型保证。
   - 对办公 Agent 或 Agent 基础设施的意义：把「经验/规程记忆写进 prompt」的验收从「模型觉得有用」推进到 **practice 上随机开关 + 成功差策展 + 可退回空 playbook**。生产可对标：跨 run 方差与「相对无记忆最差掉点」；自判标签与效应相关须报告；长生长后仍须策展而非整本灌入。

2. **[Pack Light, CarryOn: Building Object-Oriented Context for Long-Horizon Agents](https://arxiv.org/abs/2610.18784)**
   - 元信息：2026-10-13（abs：Submitted on 13 Oct 2026，v2 revised 14 Oct 2026；cs.AI / cs.CL；UCSD；项目页 ethannju.github.io/carryon）；预印本；主题标签：Context Engineering / 面向对象上下文·continuation carriers / fold 退役历史 / OSWorld 2.0·BrowseComp-Plus；分级：S
   - 核心问题：长程 Agent 进度已落在文档/表格/应用态里，却仍反复把「如何做成」的交互史塞进上下文；摘要、剪枝、外置状态仍常让续跑依赖可漂移的重构叙述。能否以**可复用任务对象**为主组织续跑上下文，并在退役历史后仍保持对象有效？
   - 机制/设计：**CarryOn** 上下文运行时。视图 \(V_t=(A_k,E_k,L_t)\)：continuation carriers（External Objects / Information Products / Situated State，带复用条件与版本）、execution context（焦点、未决约束、未物化工作）、live tail（自上次 fold 起的交互）。流程：Tracker 候选 → Grounder 只读环境校核（OSWorld：文件存在/哈希/docx·pptx·xlsx 结构等）→ Compiler 联编 \(\Delta A\) 与新 \(E\) → 校验通过才原子 fold，退役整段 live tail。宿主与 Tracker/Compiler 均为 Claude Opus 4.7；OSWorld 2.0 每任务 500 步；BrowseComp-Plus 用 BM25。
   - 证据：全量 OSWorld 2.0——partial **43.9→49.7**（+5.8）、binary **15.7→19.4**；总 token **−51.9%**、成本 **−35.9%**（含 runtime）。BrowseComp-Plus 100 题子集——准确率 **49→56**（+7），token **−22.9%**。均值输入上下文稳住约 **65K**（基线可超 200K）；至 turn 500 累积成本约 **−34.1%**。40 题子集：Sliding Window / Generic Summary 双降分；同原则的 CarryOn-Guided Summary partial 50.93，全量 CarryOn **55.93**。消融：去 execution context partial 55.93→**44.00**；去 carriers →**44.62** 且 agent calls **+23.8%**。折后 **80%** carrier 为保留或更新而非新建。
   - 局限：正文无独立 Limitations；BrowseComp 与消融为子集；Grounder 规则绑定 OSWorld 集成；fold 校验不保证任务正确性。失败条件：只做滑动窗/泛化摘要却宣称已面向对象续跑；或 fold 后只留 carrier 却丢掉未决约束；或把摘要重写当已维护跨 fold 的版本化对象记录。
   - 对办公 Agent 或 Agent 基础设施的意义：直接对标「改 pptx/docx/填表/导出」类长程桌面任务——验收钉到 **对象引用 + 复用条件 + 环境只读核验 + 未决约束显式保留**，而非越压越短的交互摘要。生产可对标：同骨干下 partial/binary 与总 token/成本分表；折后不得靠重做已落盘进度抬调用次数。

3. **[BLADE: Auditing Information Use for Failure Attribution in LLM Multi-Agent Systems](https://arxiv.org/abs/2610.18780)**
   - 元信息：2026-10-13（abs：Submitted on 13 Oct 2026；cs.AI；University of Connecticut；代码 github.com/GXG-CS/BLADE）；预印本；主题标签：Multi-Agent / 失败归因·handoff 信息使用审计 / 依赖引导 blame graph / Who&When·Who&When Pro；分级：S
   - 核心问题：多 Agent 失败时，知道信息「从哪来」≠ 知道「错在哪用」——下游可能忠实传递上游错、或误读正确源。现有依赖追踪不足以区分引入 / 传播 / 修复。如何在**无标准答案**下定位决断错误步与责任 Agent？
   - 机制/设计：**BLADE**（Blame Localization via Audited Dependency Evidence），训练免费。(1) 用 Jev 对 depends-on / repeats / contradicts / repairs 建概率依赖（阈值 \(\theta=0.3\)）；(2) 每事件至多 \(K=2\) 个高 depends-on 源做 handoff 审计，相对任务 requirement spans 判 9 类用法标签（breach / inherited·repaired / kept）；(3) 组装 blame graph \(G=(V,E,R,F)\)，全局诊断仍让**每步候选**，可推翻局部 finding。对照八策略统一挂同一 Jev 接口；评测前剥离 Who&When Pro 注入位置泄露字段。
   - 证据：1,228 条失败轨迹、五子集。宏平均 Step **57.6** / Agent **66.8**（最强基线 Step All-at-once 52.0、Agent TrajDebug 64.0）；各子集 Step 最优或并列，相对 All-at-once Step **+2.2～+11.1** pp。消融：仅依赖证据改善不稳定；加审计 finding Step **+2.4～+3.4**；打乱边/finding 或去掉 breach 均降分。选择性审计只查穷举的 **13–23%** handoff，三子集上匹配或优于穷举。全流水线约 **$1.9**/1,228 轨迹（公开输入价估算）。
   - 局限：正文 Limitations——五子集与基准域，非真实办公工作流；依赖完整轨迹，超窗缩短可能丢证据；主实验单一决策模型 Jev。失败条件：只追依赖边不审计「如何使用源」；或把局部 breach 直接当决断步；或用注入元数据/参考答案做归因。
   - 对办公 Agent 或 Agent 基础设施的意义：给「起草→检索→审批→外发」多角色流水线一条可测合同——失败复盘要能回答 **哪次 handoff 误用了正确证据**，而不只是消息拓扑。生产可对标：无金标下 Step/Agent 准度；审计覆盖率 vs 穷举；禁止用构造期泄露字段。

1. **[Copilot to autopilot: Why no single safeguard is enough](https://commandline.microsoft.com/ai-agent-copilot-autopilot-layered-model-production-network-incidents-on-call-engineers/)**

   - 局限：场景为 Azure 网络值班而非邮件/表格产品文档；文中无舰队级失败率或审批延迟分布；结晶 playbook 的准入阈值与回退策略未给量化门槛。失败条件：把 system prompt「永不」当权限边界；或给 Agent 宽服务账号+裸 shell；或让模型持有执行变更的凭据；或把「看起来安全的写」默认 auto-approve。
