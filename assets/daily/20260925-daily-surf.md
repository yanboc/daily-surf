1. **[When Can Agents Forget Their Reasoning? ICLR for Long-Horizon Agent Context Compression](https://arxiv.org/abs/2609.29875)**
   - 元信息：2026-09-24（arxiv abs；v1 submitted 2026-09-24）；预印本；主题标签：Context Engineering / 在线推理压缩 / 代理熵排序 / 状态外置可遗忘性 / WorkBuddyBench（含 Office）；分级：S
   - 核心问题：长程 Agent 不断堆积 reasoning，即便行动与观测已落地，上下文仍膨胀。与静态 CoT 压缩不同，删掉历史推理会改变后续行动与整条轨迹；需要弄清「何时可安全遗忘推理」，而不是只压短一次生成。
   - 机制/设计：ICLR（Interaction Aware Compression for Long Horizon Reasoning），无训练、在线写回。(1) 交互步 \(S_t=(R_t,A_t,O_{t+1})\)，只压缩刚完成步的 reasoning，动作/工具调用/观测/终答原样保留；(2) 按双换行切块，冻结 Qwen3.5-9B 在全史条件下算块均代理熵，删最低熵 \(\rho=0.8\) 比例块并替换为 `[SKIP]`（\(N=1\) 不删）；(3) scorer 超 42K 则跳过该步压缩，不截断行动模型上下文。辅以未来必要性探针、激活修补与「代码/文件/工具输出/环境反馈」外置态分析。
   - 证据：WorkBuddyBench Full260（DeepSeek-V4-Flash）：均值 reward \(0.699\to0.718\)，input/output/cache-read 分别约 −25.5%/−14.4%/−33.3%；W/T/L=102/76/82。Appendix E：Security \(0.478\to0.707\)（+22.9pp）主导增益；Office \(0.818\to0.776\)、Code/Web 略降。Pilot40 上 Avg 70.3 vs 多类摘要/窗/PACE 等。80 题消融：ICLR 0.738 vs Base 0.627；全删 thinking 0.718、Step-only 0.711，随机删均不及全史熵排序。轨迹放大：删 10% reasoning token 可致总 input −60.5%，删 20% 仅 −44.0%。外置态：未外置时未来行为风险 67.3% vs 已外置 36.2%；写盘后清 reasoning 规则分不变（0.759）。
   - 局限：正文无独立 Limitations；Full260 上 Code/Office/Web 域分下降且 Code input 反增；固定 \(\rho=0.8\)、依赖换行切块与跨模型代理熵；scorer 触顶即跳过压缩。失败条件：关键结论仍仅存在于 reasoning、尚未写入文件/工具结果时过早删块；或局部删除经工具选择放大成更长轨迹。
   - 对办公 Agent 或 Agent 基础设施的意义：给「改文档/跑脚本/读报错」类办公轨迹一条默认 compaction——优先砍低熵自言自语，保工具 I/O 与外置产物；生产上可把「决议是否已写入纪要/表格」当作可遗忘闸，而不是无差别摘要整段对话。

2. **[Scope Before You Persist: Preventing Cross-Family Interference in Agent Memory](https://arxiv.org/abs/2609.29144)**
   - 元信息：2026-09-24（arxiv abs；v1 submitted 2026-09-24）；预印本；主题标签：Agent Memory / 持久技能编辑 / 认证范围–检索范围对齐 / 跨家族干扰 / ORC 门闸；分级：S
   - 核心问题：冻结权重下的持久记忆（改 prompt/skill）可把局部反馈写成长期态，但「本家族证据可认证」≠「全局部署安全」——一条对某任务族正确的技能，经单一全局记忆检索后会伤害无关家族。需要同时回答是否该写入，以及写入后应在何处被取回。
   - 机制/设计：ProcStream-RSI（12 轮代码修复流、9 个可复现任务族）上比较全局 vs 家族作用域记忆。ORC（Orthogonal Regression Control）门闸：在同批 probe 上对 public/private/metamorphic 三通道做单侧 bootstrap 下界（\(\delta_{\mathrm{new}}=0,\delta_{\mathrm{reg}}=0.02\)），并要求历史族无回归后才接受 360 字符技能提案。Scoped-ORC 不改提案与门闸，只把已接受技能写入来源族槽位，检索时 \(K_t(f)\) 仅对本族返回该槽，否则回退初始技能；对照 Global-ORC 用同一紧凑全局技能覆盖所有族。
   - 证据：固定提案/决策干预（8 流）：Scoped 均值轨迹效用 0.816 vs Global 0.713 vs Static 0.775；同 8 次接受在 Scoped 有害部署 0、Global 6。27 流全长随机序：Scoped−Global 轨迹效用 +0.063 [0.037, 0.094]；接受 63 vs 12，多接受流 19/27 vs 2/27；有害/接受 0/63 vs 6/12。机制例：边界族隐式效用平均 +0.398，同时拖累 missing/rotation 等族 −0.461/−0.234 等。门闸内 public/private AUROC 约 0.752/0.998，但局部安全接受仍可伤全局——说明需范围匹配。
   - 局限：Limitations——仅九个代码契约族、单一冻结模型与可检查脚手架编辑；尚缺 compounding 的 cumulative one-shot 对照、开放世界/错槽路由、更多 editor 骨干与自动学到的不变量。失败条件：把局部认证技能写进全局记忆并无作用域检索；或路由错族时退回初始策略不足。
   - 对办公 Agent 或 Agent 基础设施的意义：企业知识工作里「合同条款 / 报销规则 / 某业务线话术」本就应按租户或流程族分槽——认证证据来自哪一族，检索就只对该族生效；可直接映射为按工作区/应用/客户分区的技能记忆，避免一条本地修复污染其他办公流程。

3. **[C3M: Cross-Session Multimodal Memory Maintenance for Long-Horizon Tasks](https://arxiv.org/abs/2609.29735)**
   - 元信息：2026-09-24（arxiv abs；v1 submitted 2026-09-24）；预印本；主题标签：Agent Memory / 跨会话多模态 / 关系感知更新 / 预算证据路由 / 源证据冷存；分级：S
   - 核心问题：跨会话长程任务要在「查询未知」时维护有界记忆：相似记录可能实体/状态/时间不同，硬合并会丢细粒度视觉线索与 provenance；只压索引又可能在读时找不到原图/原文。需要把紧凑可路由索引与可寻址源证据拆开。
   - 机制/设计：C3M。(1) Cold Store 存不可变 Raw Nodes（文本/图/溯源）；有界 active index 只存路由表示与指针。(2) RAMU：新会话构造 \(m_t=(\mathbf{z}_t,\mathcal{P}_t,\tau_t)\)，对候选预测 same/update/distinct/uncertain；仅高置信 same→Merge、update→Update（保留前后状态链），否则 Add/Keep；容量满时只合并已确认安全冗余，禁止表面相似擦除区分。(3) BMER：按页/条目/覆盖增益选候选，再在联合预算 \(\mathcal{B}\)（页、Raw Node、图像数、文本 token）下展开指针取原文原图作答。代码：https://github.com/HuzhouNLP/C3M。
   - 证据：MemLens 官方 195 题 agent 子集，在线按会话回放（未来会话与题型对写入隐藏）；共享索引/读预算（36 entries、6 pages、reader：3 页束/12 Raw/8 图/12K 文本）。GPT-5.6 Sol Overall：C3M 于 32K/64K 为 73.33/68.21，高于 MemRefine 68.21/64.62 与 CDRs 64.10/64.10；128K 上 CDRs 65.64 反超 C3M 的 63.08。Qwen 3.8 Flash：32K Overall 66.67 领先。消融：固定 C1 索引时 32K→128K 溢出修复 0→21.44/episode，Route-Hit/Support Recall/Accuracy 下降；扩索引减溢出（33.38→3.38）但准确率非单调。案例：能定位拱窗、饮水机右侧水瓶、WEGO 上方 McDonald's 等视觉细节。
   - 局限：正文无独立 Limitations；128K 长史上 Overall 可被 CDRs 超过；索引扩容与任务分非单调；评测为 MemLens 多模态回忆/更新，非办公工具副作用执行。失败条件：关系分类把 incompatible 误判为 same 而 Merge；或读预算耗尽导致指针有、原文进不了上下文。
   - 对办公 Agent 或 Agent 基础设施的意义：对应「跨周会议截图 + 纪要 + 改版表格」类企业记忆——索引做寻址、Cold Store 保可审计原件，写入时区分冗余/状态演进/冲突；落地可把权限与删除挂在 Raw Node 指针上，读路径用统一字符/附件预算，避免摘要把关键截图细节压没。

1. **[MCP Is Not Just Another API Standard](https://www.oreilly.com/radar/mcp-is-not-just-another-api-standard/)**（底层：[MCP Spec 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/)、[Tasks Extension](https://tasks.extensions.modelcontextprotocol.io/specification/2026-07-28/tasks)）
   - 元信息：2026-09-23；已发布（O'Reilly Radar 长文；作者 Balaji Venkatasubramaniyar，基于大型企业平台 MCP 集成实践）；主题标签：Agent 基础设施 / MCP 工具描述即接口 / Tasks 长程·人机审批 / MCP Apps 审批 UI / 权限·审计·allowlist；分级：S；重复出现，值得关注
   - 核心问题：把 MCP 当成「又一套 API」会低估真正变化——集成决策从「双方事先谈妥契约」变成「模型在运行时按自然语言描述组合从未约定过的工具链」；文档处理、多步审批等办公/企业工作又无法塞进单次请求，且协议层不替你做治理。
   - 机制/设计：作者把生产痛点映射到 2026-07-28 规格演进。(1) 工具描述与 schema 分工：schema 管参数形状，name/description 管「何时选用、与相邻工具如何区分」；差描述会导致自信地调错工具或带错假设。(2) 组合是涌现的：序列逻辑在模型推理里而非可单测脚本，需按「未测链路也会出现」做失败安全。(3) 规格侧：协议核心无状态（去掉 sticky `MCP-Session-Id` 以适配水平扩展）；**Tasks** 把长任务做成可轮询的 durable handle，`input_required` + `tasks/update` 承接人审/补参；**MCP Apps** 让服务器返回可内嵌交互 UI，便于人看清再批；鉴权对齐 OAuth 2.1/OIDC。(4) 治理配方：按 Agent 强制 allowlist、远程端点一律鉴权、不可变集中审计每一跳工具调用、密钥走 secrets manager 而非本地配置（防 configuration poisoning）。
   - 证据：全文基于作者「数月企业 MCP 集成」叙事；正式规格确认 Tasks 为 `io.modelcontextprotocol/tasks` 扩展、面向「Human-in-the-loop workflows — approval gates」；主规格 Security 节仍要求用户对工具调用显式同意、且工具描述默认不可信。文中给出 registry ~10k 服务器、SDK 下载量级等 adoption 旁证。
   - 局限：Vulnerability 扫描结论（路径穿越/注入/描述投毒等）为引用独立研究综述，文内无自跑复现表；allowlist/审计是架构建议而非可粘贴实现；Tasks/Apps 需客户端与服务器双向协商，落地仍依赖宿主产品。失败形态：描述过短时 Agent 选错相邻工具，问题常表现为下游「略偏」而非栈追踪。
   - 对办公 Agent 或 Agent 基础设施的意义：把「读公文→改表→发邮件/建审批」类跨系统工作流从 ad-hoc webhook 升到协议级 Tasks + 人审 UI，同时把工具文案当可审工程产物；生产上应默认：高副作用工具进 allowlist、每次调用落审计、发信/改共享盘前走 `input_required`，而不是指望模型自觉停手。

2. **[MCP Gateways: How to Manage Multiple MCP Servers at Scale](https://clickup.com/blog/mcp-gateway/)**
   - 元信息：2026-09-23；已发布（ClickUp 工程评测长文；五款 MCP 网关对照 + 迁移清单）；主题标签：办公 Agent 基础设施 / MCP 网关权限与凭证代持 / 工具面裁剪与检索 / 审计日志 / Gmail·Slack·Salesforce 等 SaaS 集成；分级：S
   - 核心问题：办公 Agent 很快会同时挂 Slack、Jira、内部库乃至 Gmail/Salesforce；每人一份客户端配置与密钥导致离职清 token、无统一调用日志，且多服务器工具定义会撑爆上下文（Anthropic 测五服务器约 55k tokens），模型在 30–50 工具后选错工具概率上升。
   - 机制/设计：把 MCP 网关定义为「客户端只连一个端点」的中间层——鉴权、按调用方过滤工具列表、前缀消歧、代持上游凭证、集中记日志；并与 registry / LLM gateway / API gateway 划界。对照五款：(1) Docker：容器隔离 + profile 级 per-tool allowlist + Desktop secrets/OAuth；(2) IBM ContextForge：虚拟服务器按团队拼工具面、REST/gRPC→MCP、OpenTelemetry；(3) Kong：与 API 同策略的 per-tool ACL 与允许/拒绝审计；(4) Bedrock AgentCore：托管语义搜工具、Salesforce/Slack/Jira 等一键集成、Cedar 策略、elicitation 中途审批；(5) Composio：1,500+ SaaS（含 Gmail/Slack）托管 OAuth、按用户会话钉工具/只读过滤、每调用或每会话人审。迁移：先 inventory 与 trust boundary 分组，只读试点再写路径，禁止 token passthrough。

   - 局限：属编辑评测而非单一厂商一手实现；用户评语为摘录；定价与「governance 版需 Sales」等会变；Composio 曾披露安全事件需纳入审查；工具搜索不能替代访问控制。失败条件：网关只记配置变更不记单次工具调用、或未裁剪工具面时 token/选错问题依旧。
   - 对办公 Agent 或 Agent 基础设施的意义：给出「跨邮件/聊天/CRM 的办公连接器」落地清单——凭证与审计进网关、发信/建单等写工具与读工具分 trust 组、按会话最小化工具面；生产上对 irreversible 工具开人审或 always-deny，并用网关日志做「谁以何身份调了哪一工具」的审计，而不是让 Agent 持有各 SaaS 长效 token。

3. **[Your AI Agents Need Undo, Not Just a Kill Switch](https://superml.dev/today)**（底层证据：[Anthropic Institute 监测度量](https://www.anthropic.com/institute/measuring-pace-of-ai-development)）
   - 元信息：2026-09-24；已发布（SuperML 工程架构长文；作者 Bhanu Pratap）；主题标签：办公 Agent 可靠性 / 可逆性分级 / 发信·CRM·工单·日程补偿 / 人机审批 / 持久化步骤日志与审计归因；分级：S
   - 核心问题：Kill switch 只能停住继续作恶，无法收回已改的 3,000 条 CRM、已关的工单、已发出的客户邮件；若 Agent 借用员工身份，审计又分不清「人写」与「Agent 写」，则无法做手术式回滚。需要在工具层按可逆性设计自治档位与恢复路径。
   - 机制/设计：四类动作契约——(1) 自然可逆（文档修订轨/软删/git）；(2) 可补偿（作废退款、重开工单、取消已排会议，saga：前进时注册补偿句柄）；(3) 可检查点（Agent 记忆/配置/检索上下文单独备份）；(4) **不可逆**（已发邮件、对外披露、已执行支付）默认必须人审。编排层以 durable step log 为真相源（工具名/参数/结果/补偿句柄 + agent run ID），下游写打 run 标签以便按 run 回滚。自主性决策树：含不可逆工具→该步人审；补偿须可程序化按 run ID 执行；检测窗口须短于传播窗口；先修好归因再扩自治。
   - 证据：架构论证辅以一手/官方数字——Anthropic Institute：约 3 万内部 Agent、在线监测 100% 预执行覆盖、八月逾十亿决策中约 0.002%（约 1/47,000）被拦，离线监测仍每千条 1–2 份 transcript 进复审（最高优先级约 50/周交人），说明预执行闸后仍有残差必须靠可逆性吸收；并引用 Cohesity/Exaforce/Akamai/Temporal 等同期产品与报告作产业对照。实施侧给出库存分级、CI 契约测补偿漂移、季度回滚演练等可操作清单。
   - 局限：Anthropic 数字为实验室自报、覆盖其最常用内部平台而非办公连接器产品；作者承认补偿漂移、级联回滚、中毒检查点恢复等新失败模式；通用 undo 引擎会错，须按域写补偿。失败条件：把 DB 时间点备份当 Agent 恢复、事后现写补偿、或工具加了 webhook 后仍按旧「可逆」分级。
   - 对办公 Agent 或 Agent 基础设施的意义：把「发邮件/改日历/批量改表/关单」从能力开关改成可测的可逆性合同——不可逆步默认 HITL，可补偿步注册反操作并写入审计 run ID；与 MCP 网关叠加时，网关管「能否调用」，步骤日志管「错了如何按 run 撤回」，二者缺一都会在办公副作用上留下不可审计的周末事故。
