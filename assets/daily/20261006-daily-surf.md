1. **[Capability-Driven Self-Evolution of Agent Memory](https://arxiv.org/abs/2610.06361)**
   - 元信息：2026-10-06（arxiv catchup / new Tue listing；abs：Submitted on 5 Oct 2026；cs.AI；USTC + Microsoft）；预印本；主题标签：Agent Memory / 能力驱动自演化 / PRISMEM·可执行记忆程序 / BEAM-1M·LongMemEval-M；分级：S
   - 核心问题：记忆自演化用任务反馈改「存/取」可执行程序时，若只看整体分做 holistic evolution，混合信号会模糊改哪里，且某一能力（事实/时序/偏好等）的突破常被别处回退抵消。能否按能力维展开搜索、保住专科增益，再合并成统一记忆程序？
   - 机制/设计：PRISMEM 将记忆程序拆为 Extraction / Indexing / Planning / Retrieval / Answer 五组件；用五类能力组织演化——事实检索 (F)、时序追踪 (T)、偏好抽取 (P)、跨会话综合 (M)、对抗/拒答 (A)。三阶段：(1) Cold start（\(T_1=5\)）用能力×组件证据诊断表快速打底；(2) Capability refinement（\(T_2=12\)）用依赖感知调度 \(\rho_t(c)=U_t(c)/(1+n_t(c))\)（直接赤字 + 最大跨能力误差压力）选目标，历史引导挑 \(K=5\) 失败案诊断并改专科程序；(3) Trace-guided integration（\(T_3=3\)）按谱系从整体最优出发，用配对差分案合并专科增益，任一能力降幅 \(>\theta=0.1\) 则回滚再试。另有压缩诊断上下文（约 −44% token）与按组件复用执行结果降演化成本。
   - 证据：在 BEAM-100K / LongMemEval-S 上演化 20 轮后，冻结程序评更长、不同内容的 BEAM-1M / LongMemEval-M。Qwen3.8-27B：BEAM-1M Overall 63.39 vs 最强静态 HippoRAG2 51.86 / 最强演化 M⋆ 52.85（+10.54～11.53 pp）；LongMemEval-M 75.50 vs EvolveMem 67.67 / A-MEM 67.33（+7.83 pp）。消融：去能力演化 −10.15；去 trace 整合 −3.16；轮询选能力 −2.55；随机选案 −5.26。演化 token：PRISMEM 73.7M（BEAM）介于 EvolveMem 与 M⋆，相对 M⋆ 约 −4%～−30%。GPT-5.5 骨干上 BEAM-1M 仍领先基线 6.17–20.41 pp。
   - 局限：正文无独立 Limitations 节。演化训练/验证题量有限（BEAM 160/120；LongMemEval 各 60），能力标签靠 LLM 离线标注（测时不喂给程序）；主指标为基准自带 LLM judge；对抗子集在 LongMemEval-M 仅 10 题。失败条件：只盯总分做反思改码（专科增益被掩）；或合并时无差分迹对比导致能力间互相回退。
   - 对办公 Agent 或 Agent 基础设施的意义：把「长伴助手记偏好/时序/跨会话事实」的记忆脚手架验收从刷总分推进到**按能力分榜 + 专科程序再整合**。生产可把「事实/时序/偏好/综合/拒答」分门回归，并把「演化只在小史、冻结后跑百万 token 史」当作记忆 harness 协议，而不是每次上线现场改检索脚本。

2. **[MemPilot: Orchestrating On-Demand Multimodal Memory Curation for LLM Agents](https://arxiv.org/abs/2610.06830)**
   - 元信息：2026-10-06（arxiv catchup / new Tue listing；abs：Submitted on 5 Oct 2026；cs.CL / cs.AI / cs.LG；NTU / 清华 / UIUC；项目页与代码见文内）；预印本；主题标签：Agent Memory / 按需多模态记忆策展 / 运行时编排·异构 LLM/VLM 路由 / 质–本–时延权衡；分级：S
   - 核心问题：多数 Agent 记忆在提问前做 query-agnostic 压缩，既浪费预处理，又丢掉日后才关键的细节；近期运行时适配又常锁死某类操作或固定流水线。能否在「预建库 vs 原始多模态史」双视图上，按质/成本/时延偏好动态决定检索还是委派策展？
   - 机制/设计：双视图——可替换的预建库 \(\mathcal{M}\) + 按 256-token 切块保留图文的原始史 \(\mathcal{H}\)。编排策略 \(\pi_\theta\)（默认 Qwen3-4B）多步决策 \(z_t\in\{\mathrm{Retrieve},\mathrm{Curate}\}\)：Retrieve 对 \(\mathcal{M}\) 语义检索；Curate 因子化控制检索查询 \(r_t\)、证据数 \(k_t\)、策展指令 \(i_t\)、后端模型 \(m_t\)、是否带原图 \(v_t\)，编排器本身不直接吃像素。用 GRPO 优化；目标维优势解耦（Q/C/L 组内分别标准化再按 \(\boldsymbol{\lambda}\) 聚合）；前缀探测边际效用 \(\Delta u_{i,t}\) 给多步 credit。偏好扫出 Perf / Bal / Cost 等操作点。
   - 证据：五基准 Mem-Gallery / WorldMemArena / H2HMem（域内）+ MemEye / MemLens（OOD）；F1 + GPT-4o-mini LLM-judge；成本含编排器与外委模型。Qwen3-VL-4B 答题：MemPilot-Perf 在五集 L-J 均为最优（如 Mem-Gallery 65.82 vs A-Mem 51.45）；MemPilot-Bal 在 Mem-Gallery F1 57.26、成本 \(1.4\times10^{-2}\) 低于多数多模态系统。Pareto：偏好扫出的质–本 / 质–时延前沿包住 LightMem / BudgetMem / OmniSimpleMem 等。消融（五集均 L-J）：去 LLM/VLM 委派 37.40→14.58；去边际效用→14.82；去目标维解耦→21.94；去检索–指令解耦→15.35。换 SimpleMem / A-MEM 预建库无需重训仍得可分前沿。
   - 局限：附录 D——外委策展可能把敏感史送出站；偏好靠预设 \(\boldsymbol{\lambda}\) 而非用户友好映射；训练用代理时延而非稳定沙箱实墙钟。失败条件：把「接了 MemPilot」当成已替代预建记忆（它正交叠加）；或 Cost 偏好下默认关视觉却仍假定能答图文题。
   - 对办公 Agent 或 Agent 基础设施的意义：把「会议截图 / 附件页 / 聊天图」长记忆从「一律预摘要」推进到**运行时按预算选检索深度、是否读原图、委派哪档模型**。生产可把 Perf/Bal/Cost 三档与「预建库可热换」「敏感史禁外委」并列入记忆服务合同，而不是只加更大上下文窗。

3. **[Attention Tax, Handoff Tax: A Stylised Model of When Multi-Agent LLM Systems Help](https://arxiv.org/abs/2610.06069)**
   - 元信息：2026-10-06（arxiv catchup / new Tue listing；abs：Submitted on 5 Oct 2026；cs.MA / cs.AI / cs.CL / cs.LG；UvA + Northeastern）；预印本；主题标签：Multi-Agent / 注意力税 vs 交接税 / 分解交叉点 / 账本对账实验；分级：S
   - 核心问题：多 Agent 文献结论分裂——有证明「同等算力下单 Agent 更信息高效」，也有「任务深度增加后分解增益上升」。分歧是否来自建模了不同瓶颈？能否用可测的「上下文退化曲线 + 交接税」给出何时该分解的交叉条件？
   - 机制/设计：风格化可靠性模型：任务 \(L\) 步，步失败率 \(\varepsilon(c,b)\) 随上下文负载 \(c\) 升、随思考预算 \(b\) 降；\(g=-\log(1-\varepsilon)\)。单 Agent 上下文 \(c_t=c_0+kt\) 付注意力税；分解系统每块 \(m\) 步重置上下文，但在边界付交接税 \(h\)（摘要相对完整上游工作区、扣回负载效应后的额外 log-loss）与写摘要开销 \(\Delta_o\)。定理：当渐近注意力税 \(a_\infty>h_{\mathrm{eff}}\) 时存在唯一交叉深度 \(L^\ast\)；曲线平坦时单 Agent 弱支配一切分解（对应 Tran & Kiela / Ao 等 skeptic 结论）。另建模冗余采样的共享失败地板与边界校验器召回。关键预测只依赖单 Agent 曲线与配对 handoff 测量，不偷看分解系统终局成功率。
   - 证据：账本对账（存款/取款/费率/hold/release/reversal；块≈400 token；同 100 本账在深度 20/50/100 配对）。模型 gpt-oss-20b，步预算 512 token，分解 \(m=5\)、handoff note≈300 token。曲线：静止类步失败从 <2k 的 2.7% 升至 >36k 的 71%。测得 \(h_{\mathrm{inc}}=0.026\)、\(h_{\mathrm{bal}}=0.010\)，预测交叉 \(L^\ast=10\)；深度 20/50/100 静止成功率：单 0.50/0.06/0.00 vs 分解 0.69/0.24/0.11（McNemar \(p\) 均显著）；终余额同向。分解系统观测成功率与预测偏差 ≤9 pp。深度 100 时两边生成 token 接近，但单 Agent prompt 约 2.0M/账 vs 分解 0.2M。
   - 局限：§11——一阶积形式忽略轨迹内失败相关（会高估单 Agent 损失，账本上方向一致）；步预算固定而非总算力池；交接税为标量、与信息论通信损失仅类比；测量仅一模型 + 账本域（及文中 pilot）。失败条件：在「曲线仍平坦」的短轨迹上强行多 Agent 交接；或只比终答却不测上下文退化与 handoff 配对税。
   - 对办公 Agent 或 Agent 基础设施的意义：给「长工单 / 多附件对账 / 跨会话流程」是否拆多 Agent 一条可测选型规则——先量注意力退化与交接税，再谈拓扑。生产可把「交叉深度前默认单线程长上下文；过交叉后按块交接并验收 note 是否保余额/状态」做成协同 harness，而不是默认「越多 Agent 越好」。

1. **[OpenShell's auto-approval sees new methods, not wider paths](https://akillness.github.io/posts/openshell-auto-approval-sees-methods-not-paths/)**（底层：[ExfilPath / capability_expansion](https://github.com/NVIDIA/OpenShell/blob/71c3cd957abef062eb7f37010056717cd49f2ed3/crates/openshell-prover/src/finding.rs)、[`finding_path_key`](https://github.com/NVIDIA/OpenShell/blob/71c3cd957abef062eb7f37010056717cd49f2ed3/crates/openshell-server/src/grpc/policy.rs)、[architecture](https://github.com/NVIDIA/OpenShell/blob/71c3cd957abef062eb7f37010056717cd49f2ed3/docs/about/architecture.mdx)）
   - 元信息：2026-10-05（Source Audit；钉 commit `71c3cd95`，合入日 2026-10-03；对照 release `openshell-prover` 0.1.2）；已发布；主题标签：Agent harness / Policy Advisor 人机审批 / auto 模式风险闸 / 方法级 vs 路径级权限 / 审计与 CI 边界 prover；分级：S
   - 核心问题：OpenShell README 承诺策略变更前用形式化验证标出「带凭证触达新主机 / 调用新 API 方法」等风险并默认等人审；若沙箱已有窄路径的凭证化 `PUT`，Agent 再提案 `PUT /repos/**`，自动批准的风险闸是否会识别「同方法、路径变宽」？
   - 机制/设计：Supervisor 是唯一出站口，REST 规则按 **method+path** 决定凭证可用范围。提案风险侧：`capability_expansion` 定义为「已有凭证触达的 (binary, host, port) 上新增 HTTP 方法」；`ExfilPath` 含 binary/host/port/category/method，**无 request path**；网关 `finding_path_key` 拼 `exfil|{binary}|{host}:{port}|{category}|{method}`，故意不含 path/policy name——「同方法复用不算新 finding」。`auto_approve_chunk` 风险闸只要 `prover: no new findings` 且 security notes 为空（notes 也不读 path）。独立 CLI `openshell-prover check --boundary` **会**比 method+path，但钉定源中网关未调用 `check_within_boundary`。
   - 证据：作者读钉定源 + 本地跑 0.1.2 prover：`base`（`PUT` 仅 docs 目录）对自身 `within_boundary`；加 `PUT /repos/**` → `exceeds_boundary` + 反例 `PUT /repos/a`，而按代码推导的 key delta 为空；加同目录 `DELETE` → boundary 拒且风险侧出现新 `capability_expansion|DELETE` key。本轮复核 `finding.rs` 对 `capability_expansion`/`ExfilPath.method` 定义及 `policy.rs` 中 `finding_path_key` / `prover: no new findings` 字符串一致。
   - 局限：审计自承未跑真 gateway/sandbox，auto 结果为代码推断；boundary 用 release 二进制而非钉定 commit 构建；非漏洞报告——auto 为 opt-in、Advisor 默认关、manual 下人仍可见完整规则。失败条件：开 `proposal_approval_mode=auto` 却把「prover 通过」当成路径最小权限已验；或只用网关风险闸、不跑 boundary CI。
   - 对办公 Agent 或 Agent 基础设施的意义：人机审批的**检查粒度**决定「已批准」含义——邮件/Drive/Sheets REST 若按 path 授权凭证，方法级 auto 闸会漏掉「同动词扩路径」。生产应：有 REST 凭证的沙箱保持 gateway-wide `manual`；需要 auto 则在 `SubmitPolicyAnalysis` validate 拦截器或定时任务跑 boundary against 运营天花板；定期 `openshell sandbox get --policy-only` + `openshell-prover check`。

2. **[MCP Server Security: What to Require Before Agents Write](https://osmanrami.fr/writing/mcp-server-security-write-access/)**
   - 元信息：2026-10-05（Osman Rami 一手工程清单；对接 ENSO MCP action server / Keycloak token exchange 实践）；已发布；主题标签：办公 Agent 写闸 / 精确参数人审 / 网关侧写分类·幂等 / WORM 审计 / OAuth token exchange·fail-closed；分级：S
   - 核心问题：常见 MCP 安全清单停在「高风险要审批、收窄 token、留审计」；Agent 真正写 CRM/ERP（及同类工单/财务写回）前，还需钉死：审批绑什么、谁判定写、重试是否双花、日志能否取证、调用带谁的权限、审批宕机怎么办。
   - 机制/设计：六条可测合同。(1) **Exact approval**：人审最终参数（工具/目标/全参），绑 hash（工具+manifest 版本+参数），改参即作废，通道 Agent 不可写；(2) **Write classification**：`readOnlyHint`/`destructiveHint` 仅 hints——版本化 **网关 manifest** 判定是否写，未知工具默认拒；(3) **Single execution**：一审批一 idempotency key 至多一次执行，重提案需新审批+前置条件；(4) **Provable log**：提案/批/拒/执行可重建，append-only 并导出 WORM（如 S3 Object Lock compliance），锁定面优先引用与哈希而非明文 PII；(5) **User rights**：RFC 8693 token exchange，禁 passthrough 与万能服务账号；(6) **Fail closed**：审批/策略/日志不可用则停写；审批过期，超时永不默批。
   - 证据：全文六要求表 + 每条 Test（改参后重提须拒、伪标 read-only 仍须审、双发/改参/重提案各一次执行与两次拒、停审批服务后零执行）；对齐 MCP Tools/Security（HITL 不可协议强制、注解不可信）、Authorization（禁 token passthrough）、OWASP LLM06、Stripe idempotency、EU AI Act Art.14；文末指向 ENSO 单 action server + Keycloak/OIDC + IRSA 落地。
   - 局限：不覆盖 prompt injection/供应链；不排名网关产品；legacy 无 token exchange 时只能网关侧代执用户权（更弱）；定时无用户 Agent 仍可能滑回窄身份服务账号。失败条件：把模型摘要当审批对象；或信任服务器自报 `readOnlyHint`；或审批不可用时仍放行写。
   - 对办公 Agent 或 Agent 基础设施的意义：发信、改表、建日程、写回业务记录的验收应问「批准绑定终参？重试会双花？宕机是否 fail-closed？下游日志能否点名 Agent+用户？」——与 Airlock 冻结参数预览、Fullmakt 受众隔离、Gatekeeper 同步人审写同一轴。生产采购可要求演示：批一次→重试→改参→停审批，四步缺一即未达标。
