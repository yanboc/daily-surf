1. **[What to Admit and How to Present: Governing Persistent Memory in LLM Agents](https://arxiv.org/abs/2610.11188)**
   - 元信息：2026-10-08（abs：Submitted on 8 Oct 2026；cs.AI；Pazhou Laboratory；拟投 AAMAS 2027）；预印本；主题标签：Agent Memory / 准入 vs 呈现分治 / 情境裁决·FC·PS / PersistBench·MemSyco-Bench；分级：S
   - 核心问题：持久记忆常被整段 verbatim 注入，生成器同时要解决「要不要用」与「怎么表述」——易诱发迎合与跨域泄漏。能否在不改库、不重训的前提下，把**准入（admission）**与**呈现（presentation）**拆成两根可测杠杆，并量化各自效应？
   - 机制/设计：检索 top-\(k\) 后做一次**情境裁决**（同批看 query、对话、证据与全部记忆，只标 kind/subject/epistemics/temporality 等属性，不定动作）。两套准入：**(FC)** 整条目打因素 → 确定性规则编入五类 typed channel（约束/个性化/非权威观点/支持/不确定；信念与未核实事实 fail-closed）；**(PS)** 先拆 typed unit → 映射到五类许可用途或 deny，deny 物理移出 prompt。呈现对照：同一裁决结果下 **PN**（许可说明头）vs **CH**（通道头）。对照：verbatim Bare、MemGate 式 query-conditioned Gate、NoMem。开发面 PersistBench（迎合/有益使用/跨域泄漏）；外部面 MemSyco-Bench 四任务×300（ofj / csc / mec / pm）。
   - 证据：外部相对 Bare，FC/PS 合并失败率 46.2%→39.5%/37.4%（−6.7/−8.8 pp，\(p=2.7\times10^{-7}/4.1\times10^{-12}\)）；ofj 失败 45.2%→20.4%。Gate 对 ofj 几乎不动（45.2%→45.5%，\(p=1.0\)），合并 \(p=.08\)。等预算下 PS 优于随机与相关性选元（Holm）。开发面跨域：Qwen3.7-Max 44.0%→14.5%、Kimi-K2.6 37.0%→22.5%。固定呈现只收紧准入：跨域再降 17.5 pp（\(p=1.6\times10^{-4}\)）。裁决固定时 PN vs CH 九格仅一格名义显著，BH 后不成立。mec 误导在治理臂仍 82.3–85.0%（Bare 91.7%；NoMem 0%）。
   - 局限：正文 Boundaries/威胁——两设计均抬高个性化漏用（FC +7.6 / PS +5.3 pp）；PS 未过预注册门（合并改善需 ≥10 pp、且无任务准确率降 >3 pp；实得 8.8/−6.0）；GPT-OSS-120B 泄漏无显著改善；外部单生成器+单裁判（开发 rubric 人机 \(\kappa=0.70\)）；情境权限探针上 PS 无显著选优。失败条件：把「相关即准入」当治理（Gate 在 ofj 失效）；或只换呈现措辞却保留冲突记忆进上下文；或用 NoMem 零误导证明已修好 mec（同时毁掉个性化收益）。
   - 对办公 Agent 或 Agent 基础设施的意义：把「用户偏好/持仓/简历」类长期记忆验收钉到**写入后的生成前准入**——属性裁决与动作策略分离、不合格 unit 物理缺席。生产可对标：ofj/csc 与个人化漏用分表报告；冲突记忆默认拒入而非改措辞；Gate/相似度闸不得单独宣称已抑迎合。

2. **[REMORY: Learning Residual Memory for Context Compaction](https://arxiv.org/abs/2610.11287)**
   - 元信息：2026-10-08（abs：Submitted on 8 Oct 2026；cs.CL / cs.AI；上海创智学院 / 复旦等）；预印本；主题标签：Context Engineering / 残差软记忆补压缩摘要 / 冻结 Actor 续写匹配 / SummHay·BrowseComp·Terminal-Bench·AutomationBench；分级：S
   - 核心问题：长程 Agent 反复 `/compact` 后只留可读摘要作检查点，后续决策未必都能由摘要支撑，而事先枚举「摘要外还缺什么」又不可行。能否在**保留文本摘要与档案检索**的同时，学一段有界软 token，补上摘要留下的预测缺口？
   - 机制/设计：**REMORY** 在压缩边界 \(i\) 上，由历史 \(H_i\) 与新摘要 \(S_i\) 生成 \(M_i=C_\phi(H_i;S_i)\)，\(|M_i|\le m\)，拼接 \([S_i;M_i]\) 作为序列维「残差」。网络用冻结 Actor 特征与 learned queries 并行出记忆向量，分层压缩上限 4,096 slots（约每 1,024 源位→64 soft）。训练两阶段、Actor \(p_\theta\) 冻结：**(I)** 重建——学生用 soft memory 逼近教师对源文的复述；**(II)** 摘要条件续写——教师见全历史、学生见固定摘要+记忆，对学生↔教师 reverse KL。Qwen3.8-27B / GLM-5.3-Flash 上记忆网分别约 1.94B / 1.50B 可训参数；精确记录仍走普通 archive/文件工具。
   - 证据：SummHay 92 查询——Summary+REMORY 相对 Summary：Citation F1 +4.04、Joint +3.55、Coverage 仅 +0.40；用 raw 上下文 5.2% 的位置逼近 raw 的 joint（43.39 vs 43.41）；等预算 Summary++ 几乎无增益。BrowseComp / Terminal-Bench 2.1：Qwen 74.0→77.0 / 71.9→76.4；GLM 84.9→89.0 / 84.3→87.6；重复工具输出 −17.9%～−29.8%、工具错误 −25.3%～−49.7%。AutomationBench / JobBench（Qwen，5 run）：35.5→45.3 / 33.4→41.0。488 对压实后首动作偏好：残差胜 70.7%。Cell-segmentation 案例：摘要漏编辑命令时靠摘要+记忆+重读文件恢复并通过 9 项 verifier。
   - 局限：正文无独立 Limitations；从实验可知——Live Trading ROI 轨迹市场选择不同、不可作因果收益证明；首动作研究是反事实提案评判而非执行结果；成本只计 Actor/摘要 token，不含记忆网前向；需按骨干训练专用接口；案例不证明「漏掉的细节来自记忆通道」。失败条件：把 REMORY 当跨会话长期事实库（它补单次会话压缩缺口）；或关掉 archive 检索却假定 soft token 可替代精确记录；或每步重渲摘要却不维护残差槽。
   - 对办公 Agent 或 Agent 基础设施的意义：把办公长工单「摘要检查点」推进到**可读摘要 + 有界残差软记忆 + 工具取原文**三层合同。生产可对标：压实后首步动作质量、重复工具/报错率、Attribution/Coverage 分项，以及记忆槽位数与前缀缓存策略一并回归。

3. **[Error-Propagation Modeling for Failure Attribution in LLM-Based Multi-Agent Systems](https://arxiv.org/abs/2610.11600)**
   - 元信息：2026-10-08（abs：Submitted on 8 Oct 2026；cs.AI；国科大/国防科大等；文内 Copyright ©2027 AAAI）；预印本；主题标签：Multi-Agent / 错误传播·持久交互环 / 反事实决断步归因 / Who&When；分级：S
   - 核心问题：多 Agent 失败时，日志里多个「错步」混杂——有的已被纠正，有的只是下游症状。归因目标应是**决断错误（decisive error）**：修正该 agent–step 后执行可恢复成功（Who&When；多候选时取最早）。仅挑可疑步、不建模传播与未解环，如何区分根因与症状？
   - 机制/设计：**EMFA** 五段：(1) 从 query 抽成功规约 \(C_{success}\)，在末 \(w=5\) 步锚定最终失败症状；(2) 将扁平轨迹建成子任务/步级依赖 \(H=(X,S,E_{step},E_{sub})\)；(3) 自症状反向相关追溯得 \(G_{info}\)，再按时间用 LLM 标注引入/传播/变换/纠正 → \(G_{prop}\)，并独立抽取未推进目标的持久环 \(G_{loop}\)；(4) 传播支路与环支路各筛 ≤2 候选并去重；(5) **模型反事实验证**（非环境重放）判断最小修复能否阻断下游失败，辅以责任边界规则（计划作者 vs 执行者等）选出最早决断对。
   - 证据：Who&When——Hand-Crafted 58 条（Magentic-One）/ Algorithm-Generated 126 条（CaptainAgent；任务来自 GAIA、AssistantBench）。Step_ACC：32.76% / 50.00%，相对原 SOTA CHIEF +3.45 / +4.40 pp；Agent_ACC：74.14%（Hand 最优）/ 66.67%（Alg 次优级）。消融：去掉传播支路 Step 崩至 1.72% / 13.49%；去掉环支路 Alg Step 50.00%→33.33%。骨干换 GPT-4o 最优；长轨迹分档上 step 仍相对稳，部分长档 agent 准确率下降。
   - 局限：正文 Conclusion and Limitations——显式结构化与传播建模带来额外推理开销；结构先验可能漏掉未建模失败模式；反事实为模型评判而非真实重跑；Step_ACC 绝对水平仍低（约 1/3～1/2）。失败条件：把最终答错步当决断步；或只用单次 LLM「谁错了」而不建传播/环；或有任务标准答案 \(G\) 才归因（主实验刻意不用 \(G\)）。
   - 对办公 Agent 或 Agent 基础设施的意义：给「调研→撰稿→审阅」类办公多 Agent 一条可运维归因合同——**先建依赖与传播/死环，再反事实验证最早可修复步**。生产可把「计划错 vs 执行错」「环内空转」写进值班手册，并与拓扑诊断（如 MAScope）互补：一个问结构形态，一个问时间线上的决断步。

   - 证据：[README](https://github.com/genspark-ai/genoffice/blob/ab53f5bd/README.md)（AI you can review / CLI·MCP）；[Release v0.11.411](https://github.com/genspark-ai/genoffice/releases/tag/v0.11.411)；[`redact-range.ts`](https://github.com/genspark-ai/genoffice/blob/8feee6ae/packages/agent-core/src/redact-range.ts)；[`redact-core.ts`](https://github.com/genspark-ai/genoffice/blob/8feee6ae/packages/agent-core/src/redact-core.ts)；PR [#1882](https://github.com/genspark-ai/genoffice/pull/1882)/[#1886](https://github.com/genspark-ai/genoffice/pull/1886)；测 `packages/agent-core/tests/redact-range.test.ts` / `redact-core.test.ts`。
   - 局限：脱敏是**应用内模型读路径**合同，不是文件级加密——MCP/CLI/导出可见原文；无 marker 的静默排除（如统计跳过某格）不在共享核承诺内；跨编辑器 mark 名须一致。失败条件：把「已隐藏」当成对所有 Agent 通道保密；或依赖抛错回退路径。
   - 对办公 Agent 或 Agent 基础设施的意义：把「人保留全文、模型只见占位符」做成可测的共享核，堵住选区回引泄漏。生产可对标：一切喂模型的 `textBetween` 必须走 redact walker；占位符往返校验；对外通道（MCP/导出）单独声明可见性，勿与 UI 隐藏混为一谈。

   - 核心问题：多数产品把 HITL 做成「人人点过的确认框」或「事后看一眼输出」——既非控制。财务/运营 Agent 要碰发信、过账、改价、删记录时，闸门应放在哪、绑什么、谁强制、如何证明门在工作？

3. **[The Outer Loop, Insights First: An Ambient Quality Agent That Diagnoses Your Production Agent](https://developers.googleblog.com/en/the-outer-loop-insights-first-an-ambient-quality-agent-that-diagnoses-your-production-agent/)**

   - 核心问题：上线后 Agent 仍可 HTTP 200、延迟正常、工具无报错，却在对话内静默失败（如未问座位子 Agent 就写死座位、跨 Agent 丢饮食偏好）。如何在请求路径外持续把生产轨迹变成可验证、可锚定代码的洞察，再喂回内环修复？
   - 机制/设计：**AQuA** 旁路驻留同一 GCP 项目：按调度/部署后/按需从 Cloud Trace、Logging 或 BigQuery 抽样 ≤1,000 会话；永不入请求路径、不回写被测 Agent；原文与部署源码快照不出项目边界。五段流水线：Sample → Review（九项清单 + `goal.md` + 可选 AutoRaters/`eval_config.yaml`，失败写 actual/expected）→ Cluster → Verify（另一模型对每簇最多 3 份全文 transcript，不支持则丢弃）→ Track（BigQuery 上 NEW/RECURRING/14 天未见自动 RESOLVED）。根因分析按需触发：对照部署修订的不可变源码快照，缺陷在仓内则引 `file:line` 并提出锚定编辑，在仓外则归因轨迹步骤；**从不自行改码或开 PR**。travel-concierge 演练：32 会话 / 1,583 spans；42 findings → 9 候选簇 → 验证剔 3 → 6 已验证问题（座位旁路 15 会话、vegan 跨 Agent 丢失 7、poi 空工具表却要求地图字段 5）。修两处 prompt 后同剧本：座位旁路 15→2（−87%）、vegan 7→0、全会话通过 5→13/32。

   - 局限：正文 Hard problems——随机抽样难捕 1% 静默回归；模型裁判与 SME 对齐仍难；验证封顶 50 簇；超长轨迹需压缩；静态 replay 难复原外部环境。ADK 1:1 sidecar，舰队 1:N 仍在探索。失败条件：把「基础设施全绿」当任务成功；或把未验证簇当已证实缺陷自动合入。
