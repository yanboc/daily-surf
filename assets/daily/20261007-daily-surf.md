1. **[MINDSET: Energy-based Schema Evolution for Long Conversational Agent Memory](https://arxiv.org/abs/2610.08586)**
   - 元信息：2026-10-06（abs：Submitted on 6 Oct 2026；cs.AI；Mahindra University）；预印本；主题标签：Agent Memory / 版本化 schema·最小能量转移 / 不可变 episode·出处扩展检索 / LoCoMo·MemoryAgentBench；分级：S
   - 核心问题：长对话里指令与偏好会变——只留最新态会丢变迁证据，扁平向量库又把矛盾丢给答题模型反复消解；摘要改写又会抹掉可核验原文。能否在不调用 LLM 重写历史的前提下，用显式状态转移组织记忆，并按查询取「当前/历史/语境」证据？
   - 机制/设计：MINDSET 将对话存为不可变 episode（对话 ID、时间、说话人、原文 + 本地抽取的实体/角色/语境/属性/变更线索），上层维护版本化 schema（support/exception、质心与 medoid、有效期、active/historical、前后继）。新 episode 在候选动作 \(a\in\{\mathrm{reinforce},\mathrm{supersede},\mathrm{split},\mathrm{new}\}\) 上选最低能量可行转移：兼容度 \(K\) 由 dense 相似度与实体/角色/语境/话题重叠加权；矛盾 \(p\) 只对单值槽做 Jaccard；时序势 \(\tau\)、语境势 \(\kappa\) 门控 supersede/split。能量 \(E(a)=w_d D_a+w_c C_a+w_h H_a+w_f F_a+w_i I_a\)（畸变、未解矛盾、历史损伤、碎片化、内部不一致），实现权重 \(\mathbf{w}=(1.00,1.25,0.75,0.22,1.00)\)；滞回用 switch/stay margin（如 \(m_{\mathrm{switch}}=0.18\)、孤立强矛盾先 reinforce 并记 exception）避免单次冲突过早改写稳态。检索：路由器标 current/historical/contextual/generic，再融合 direct（dense∪BM25）、schema 扩展回 support/exception/medoid、version medoid；统一证据预算（最多 8 段、8k token）把原文 episode 交给答题模型。写入/检索无 provider LLM 调用。
   - 证据：冻结清单 850 题（LoCoMo-700：10 会话×70；类别含 single-hop/temporal/multi-hop/open-domain/adversarial；MAB-150：125 ICL+25 推荐）。GPT-OSS-120B：Answer F1 0.4280 vs LightMem 0.4024 / Vector RAG 0.3807；Recall@8 0.6280 vs 0.4522；MRR 0.5572 vs 0.4365；nDCG@8 0.5453 vs 0.4092；对 LightMem 的 Recall@8/MRR/nDCG@8 经会话簇置换检验 Holm \(p=0.00977\)，F1 对 LightMem 未显著（\(p=0.240\)）。消融：最近邻合并 −0.020 F1、去碎片化惩罚 −0.0237。跨骨干：GLM-4.7 上仍领先；Gemma-4-31B 上 F1 与 LightMem 几乎持平（0.3306 vs 0.3308）但检索仍第一。相对 Long Context token 约低一个数量级（约 0.40M vs 4.31M）。
   - 局限：正文 Limitations——MAB ICL 绝对分极低（exact match 仅 0.024）、推荐仅 25 例；LightMem/MemoryBank 为复现（上游产物不可用，MemoryBank 摘要器换成 GPT-OSS）；转移系数与滞回阈为开发集手调、非最优证明。失败条件：把 schema 当可丢原文的摘要；或无证据预算对齐就横向比 F1；或在未校准滞回时把单次矛盾当成 supersede。
   - 对办公 Agent 或 Agent 基础设施的意义：把「偏好/计划/岗位变更」长记忆从「越摘要越好」推进到**不可变事实 + 版本态索引 + 查询时回放出处**。生产可把 reinforce/supersede/split 对应「追加证据 / 关旧开新 / 语境分支」，并把「答题只吃有界原文包、写库不调大模型改写」写进记忆服务合同。

2. **[Beyond Corrected Memory: Execution Consistency in Multi-Agent Systems](https://arxiv.org/abs/2610.08101)**
   - 元信息：2026-10-06（abs：Submitted on 6 Oct 2026；cs.AI；HKUST(GZ) + SUTD）；预印本；主题标签：Multi-Agent / 共享记忆之上的执行一致性 / 职责·证据充分性·N/V/U 判定 / CAVERT 诊断与提交前闸；分级：S
   - 核心问题：共享记忆「记录正确」或任务「表面成功」并不能保证执行满足任务职责——例如采购 Agent 在收到审批撤销后仍下单。相同留存记录可否对应合规与违规两种轨迹？判定需要哪些执行证据，缺证据时应标 undetermined 而非默认合规？
   - 机制/设计：定义执行一致性为：相对公开合同 \(P\) 与执行记录 \(T\)，对状态使用、信息交接、终态一致三类职责做证据充分判定。十二机制分属 Strict-temporal（冲突写入、陈旧依赖、未解矛盾）、Causal-semantic（漏交接、无支持假设、无支持重建、源范围/视图丢失、证据状态升级）、Eventual-semantic（终态分歧、竞争终答、终态证据未决）。单条 finding 走四问：可疑问题 \(C\) → 谁在何时须做什么 \(O\) → 相关过程是否被充分观测（认证窗口 \(W\)）→ 响应是否履行且截止前仍有效 \(D\)；结论为 N（无违规）/ V（违规）/ U（证据不足）。CAVERT：LLM 做范围过滤与因果-状态抽取并对源引用做检查，再用确定性规则出裁决（不调 LLM）；Core gate 在提交前拦截（如用已废审批下单则先公共读刷新再提案）；已落地外部副作用需另做补偿，不在当前闸内。
   - 证据：RQ1——AgentWebBench / MARBLE / MECoBench 上 450 对受控删除-恢复（五因子：消费方 receipt、动作依赖、授权、历史版本资格、截止时修复有效性）；398 对 N/V 相反标签中，删证据后 82.4% 留存输入不可分，恢复后 97.9% 再可分（簇级 95% CI [78.1%,86.2%] / [95.8%,99.1%]）。自然日志 360 条中 43 V，unsupported assumption 占违规的 67.4%。RQ2——720 执行、12 个 benchmark×executor：CAVERT Acc 87.1% / macro-F1 83.5% vs Contract LLM 80.6/74.8、Rules 78.9/73.8；同预算 $0.012 下仍领先。RQ3——AppWorld / LongCLI / MARBLE / CoffeeBench 各 180 匹配故障块：同闸下 AppWorld 成功 89→122/180（+18.3 pp）、LongCLI 无回归修复 51→75（+13.3 pp）；相对 MemTX 归一化分 +8.75 pp；无注入故障 480 块上相对 Native −0.7 pp 满足非劣；长程队列约 +24.6% token / +5.0 s。
   - 局限：附录 E.5——主张限于所评合同、证据因子与日志变换；自然频率仅刻画抽样源；CAVERT 从现有日志恢复关系，诊断质量受抽取上限；闸只拦未提交写，已提交副作用需补偿机制。失败条件：只验「记忆库最终值一致」却不记 receipt/依赖/截止有效性；或在缺覆盖时把 U 当成 N；或指望 gate 自动回滚已对外部系统生效的写。
   - 对办公 Agent 或 Agent 基础设施的意义：把多 Agent 办公（审批撤销后的采购/改单、跨 Agent 交接）的验收从「共享记忆对不对」推进到**职责履行是否可证**。生产日志与记忆接口应保留 receipt、谁用了哪版状态、工具效应是否持续到 deadline；人审/自动闸可对 U 与陈旧依赖做提交前刷新，而不是只做记录纠错。

3. **[SquidAgent: Parallelize Wisely, Coordinate Efficiently](https://arxiv.org/abs/2610.08647)**
   - 元信息：2026-10-06（abs：Submitted on 6 Oct 2026；cs.AI / cs.CL / cs.LG；Sydney / MBZUAI 等；comment：Accepted at NeurIPS 2026）；预印本（NeurIPS 2026 已接收）；主题标签：Multi-Agent / 并行化判据·再探索税与对齐税 / 会话 fork·约定块·层调度 / 吞吐 vs 质量；分级：S
   - 核心问题：多 Agent 并行本应加速，却常慢于单 Agent——因工人要重建编排器已有上下文（再探索成本），以及独立产出要对齐（对齐成本）。能否用可估代价决定「这一层该串还是并」，并把两类隐成本压成可调度项？
   - 机制/设计：编排器一步产出任务 DAG、每子任务输出 token 预算 \(\tau_i\) 与层对齐预算 \(\widehat{C}_{\mathrm{alg}}\)。层代价：串行 \(T_{\mathrm{ser}}=\sum\tau_i\)；并行 \(T_{\mathrm{par}}=\max\tau_i+C_{\mathrm{exp}}+C_{\mathrm{alg}}\)。因墙钟难估、LLM 对时长校准差，改用输出 token 作代理。SquidAgent 设计消项：worker **fork 编排器会话**使 \(C_{\mathrm{exp}}\approx 0\)；并行前写**共享 convention block**把对齐前移为有界 \(\widehat{C}_{\mathrm{alg}}\)；有效并行代价 \(\widetilde{T}_{\mathrm{par}}=\max\tau_i+\widehat{C}_{\mathrm{alg}}\)，比率 \(\hat\rho=T_{\mathrm{ser}}/\widetilde{T}_{\mathrm{par}}\)，仅当 \(\hat\rho>\alpha\)（默认 \(\alpha=1.9\)）才并行，否则串行以防估计噪声。另有小任务（估计 <3000 token）强制串行。确定性按拓扑层调度。
   - 证据：统一 Claude Sonnet 4.6（thinking medium）；9 任务（PixelCraft/ShopFlow/CompressKit/ArcadeBox/SlideKit/ClimateAnalysis/LinAlgBook/MathRef/CloudDocs）。吞吐（交付词/墙钟）：SquidAgent overall 38.1 vs Claude Code 17.2（×2.2）、最强多 Agent AgentConductor 19.2（×2.0）；ArcadeBox/SlideKit 相对最强基线约 ×2.8 / ×2.3。质量（Claude Opus 4.6 二值量表）：98.2±2.1% vs Claude Code 97.1±3.1%。消融（四任务均值吞吐）：去调度 42.93→29.14（−32.1%）、去 session fork→30.88、去 convention→32.63。预测校准：输出 token 与观测 Spearman \(\rho=0.77\)，墙钟仅 0.16。\(\alpha\) 敏感：MathRef 上 \(\alpha\geq 2.0\) 把紧耦合 L1 改串行可提到 45–51 words/s。
   - 局限：附录 H——token 预算可偏 2–5×，全局 \(\alpha\) 非按层置信度自适应；token 代理不覆盖工具/检索/外 API 时延；层级同判可能错过层内大小任务混部。失败条件：在工具密集办公流上仍只用生成 token 估并行收益；或无 fork/约定块却「能并就并」；或 \(\alpha\) 过低把紧耦合交叉引用层强行并行。
   - 对办公 Agent 或 Agent 基础设施的意义：给「多文档/多模块知识工作」一条可测协同 harness——**先估串并对齐税，再决定并行**；会话继承与约定块把交接税前移。生产可把「层比率门槛 + 小任务串行 + 约定块验收」并入多 Agent 编排，而不是默认 Agent 越多越快。

   - 证据：[README](https://github.com/NVIDIA/OpenShell/blob/360c5a0/README.md)、[architecture](https://docs.nvidia.com/openshell/latest/about/architecture)、[network-rules（WebSocket / uninspected）](https://github.com/NVIDIA/OpenShell/blob/360c5a0/docs/how-it-works/policies/network-rules.mdx)；Issue [#3942](https://github.com/NVIDIA/OpenShell/issues/3942)；PR [#4171](https://github.com/NVIDIA/OpenShell/pull/4171)；实现 [`openshell-policy` `merge.rs`](https://github.com/NVIDIA/OpenShell/blob/360c5a0/crates/openshell-policy/src/merge.rs)（`allow_uninspected_credentials` ∈ `endpoint_attributes_cover`；`enabling_an_endpoint_flag_requires_the_whole_binary_scope`）。
   - 局限：修复落在策略合并层，不替代 Policy Advisor/prover 对人审粒度的既有限制；#4171 未跑 openshell-server/Z3 E2E；多 binary 共 rule 仍是运维易错模式。失败条件：假定「只给 A 开 uninspected」不会波及同 rule 的 B；或把 flag 当默认安全捷径而非显式例外。
   - 对办公 Agent 或 Agent 基础设施的意义：给「邮件/日历/Chat REST+WS 共 rule」的凭证例外一条可测合同——**扩危险旗标必须点名全部受影响 binary**。生产可把「A-only update 必拒」「全 binary 命名才过」「未命名 binary 仍 1008」列入策略 CI，与 Advisor manual/boundary 闸并列。
