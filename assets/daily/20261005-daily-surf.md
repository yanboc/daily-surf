1. **[APDMem: Agent-Controlled Progressive Disclosure for Query-Adaptive Long-Term Memory](https://arxiv.org/abs/2610.02472)**
   - 元信息：2026-10-05（arxiv pastweek / new Mon listing；abs：Submitted on 1 Oct 2026；cs.CL；JPMorgan Chase ML CoE）；预印本；主题标签：Agent Memory / 渐进披露检索 / 多分辨率记忆层 / LongMemEval-S；分级：S
   - 核心问题：个性化长程助手要从跨会话历史捞稀疏证据，但查询复杂度不一——简单题不该把整段原文灌进上下文，复杂时间/多跳题又需要逐字细节。扁平库或固定粒度检索会在「成本」与「保真」之间二选一。能否让 Agent 按查询自适应决定披露到哪一层？
   - 机制/设计：APDMem=\(L_0\)–\(L_3\) 多分辨率基底 + Progressive Disclosure Controller + Organized Notes Synthesizer。每会话四层：\(L_0\) 主题摘要（含消歧代词/归一日期/关键词，作主索引）；\(L_1\) 个性化关键事实；\(L_2\) 按时间序的 turn 级证据笔记；\(L_3\) 原文消息。写时只物化 \(L_0\)/\(L_3\)，\(L_1\)/\(L_2\) 懒生成并缓存。Controller 工具集：`search`（\(L_0\) 上 BM25+稠密 RRF）、`read_facts`/`read_turns`/`read_raw`、`interpret_dates`、`decompose`、`reflect`；目标是在 \(T_{\max}=20\) 步内以最小访问成本凑够答题证据。收敛后先出 draft，再经 notes 合成（事实/时序/矛盾/计数证据）交给生成器。
   - 证据：LongMemEval-S（500 题）。GPT-4.1：APDMem 87.8 vs SimpleMem 84.0 / LightMem 76.9 / Mem0 58.5；GPT-4.1-mini：79.8 vs 76.9。SS-Asst 上 GPT-4.1 达 100.0（SimpleMem 76.8）。行为：平均只钻入 haystack 8% 会话（3.7/47.7）；1,838 次 drill 中 73.7% 停在 \(L_1\)、20.2% 到 \(L_3\)。消融（GPT-4.1）：去 Controller→层次化 RAG 83.2（−5.2%）；Vanilla RAG（仅 \(L_3\)）77.0（−12.3%）；去 \(L_1\)/−3.6%、去 \(L_3\)/−5.9%、去 reflect/−3.6%。效率（GPT-4o-mini）：离线构建 145.4k tok / 101.5s vs Mem0 1,152k / 4,248s；固定生成器时只升级 Controller（mini→4.1）79.8→86.8。
   - 局限：Limitations——召回依赖 \(L_0\) 摘要保真，摘要漏细节会拉低 BM25/稠密分；\(L_1\)/\(L_2\) 懒物化有冷启动时延；未显式建跨会话图边。Multi-S. 上 GPT-4.1 77.4 低于 SimpleMem 81.2（广度 vs 深度权衡）。失败条件：把 \(L_0\) 当最终证据却从不 drill 到 \(L_3\)；或关闭 reflect 导致过早收敛/空转检索。
   - 对办公 Agent 或 Agent 基础设施的意义：给「客户偏好 / 项目往来 / 跨会话事实」一条可验收读合同——粗摘要先筛、关键事实常停、逐字细节按需下钻。生产可把「简单题不得默认读全文」「verbatim 题必须能落到 \(L_3\)」「Controller 与 Generator 可异构配预算」做成记忆 harness 回归门。

2. **[DyadMem: A Long-Term Memory Benchmark of How Agents Work with Users](https://arxiv.org/abs/2610.03020)**
   - 元信息：2026-10-05（arxiv pastweek / new Mon listing；abs：Submitted on 2 Oct 2026；cs.AI；NTU/NUS/HKU/Stepfun；文内标注 Date: October 5, 2026）；预印本；主题标签：Agent Memory / URAM 用户条件关系记忆 / Capture·Update·Recall 全流水线 / Gold-Memory vs Full-Pipeline QA；分级：S
   - 核心问题：长程 Agent 不仅要记「用户是谁、偏好是什么」，还要记「这个 Agent 与该用户该怎么协作」——同一用户、不同交互史应导向不同行为（URAM）。既有基准多只监督用户侧事实，或只看终答 QA，会掩盖「建库/更新/检索」哪一环坏了。
   - 机制/设计：DyadMem 在同一多会话轨迹上联合标注用户侧（`user_profile`/`fact`）、URAM（`agent_identity`/`agent_method`/`agent_knowledge`）与共享 `episodic`，共 6 类。规模：3,065 episodes、50,961 sessions、61,210 QA；会话级 Capture 与 Update（增/删）、查询级 Recall 支撑集。评测拆开：Capture F1；gold-conditioned Update op-F1（Add/Del）；Recall@n；Gold-Memory QA（直接给金支撑）；Full-Pipeline QA（模型自建库→召回 \(K\leq16\)→答题），并定义 \(\Delta_{G2P}=\mathrm{Acc}_{gold}-\mathrm{Acc}_{pipe}\)。对话优先合成后由 9 人质检（保留率 76.6%）；QA 默认 GPT-5-mini 判分，matcher 为 BGE-M3+NLI。
   - 证据：20 模型。开源均：Gold-Memory 90.61 vs Full-Pipeline 47.73（\(\Delta_{G2P}\)≈42.9）；专有均 91.22 vs 57.35（≈33.9）。Capture 呈高精低召（开源 P 53.95 / R 15.13）；Update op-F1 开源 18.55、专有 24.47；不安全删除率开源/专有均约 84%/78%。Recall@n 领先模型仍 <63%，但 Hit@1 可达 85–89%。Kimi-K3 Full-Pipeline 最高 74.85，但 Capture R 仅 18.55、Update 31.69，且 7.94% 正分答无检索支撑。URAM vs Agent-only：20/20 模型 Update 正向；URAM-only QA 开源均 +3.20、专有 +3.67（DeepSeek-V4-Pro +9.77）。用户中心 Full-Pipeline 开源均 40.31 vs Agent 中心 55.08（差 14.8），而 Capture/Recall 差距仅约 3.4/0.9。
   - 局限：附录 C——语料全为合成多会话，非真实用户日志；无独立 Limitations 节，但 §4.7 明示 Full-Pipeline 会被拒答风格扭曲（如 Qwen3-4B OA 16.2% 却因少拒答压过更强阶段指标的 Qwen3.5-9B）；金标 Update 主评与上游错误隔离，端到端 \(\Delta_{G2P}\) 非因果分解。失败条件：只用终答 Acc 选型（可掩盖空库/乱删）；或把 Agent-only 经验记忆当已覆盖「对该用户该怎么做」。
   - 对办公 Agent 或 Agent 基础设施的意义：把办公长伴助手的记忆验收从「能答对」推进到 **Capture/Update/Recall + 关系侧 URAM**——要记协作程序、角色边界与用户条件决策规则，并单独盯误删。生产可把「金支撑答题 vs 全流水线落差」「删除精确率」「用户侧 vs Agent 侧分榜」列入记忆回归门，而不是只刷 LongMemEval 总分。

3. **[Trained Agentic Context Management](https://arxiv.org/abs/2610.02404)**
   - 元信息：2026-10-05（arxiv pastweek / new Mon listing；abs：Submitted on 1 Oct 2026；cs.LG；代码 brycesandlund/infinite-context）；预印本；主题标签：Context Engineering / 训练式上下文管理 / 最小 harness·子 Agent 分解 / RULER·OOLONG-synth；分级：S
   - 核心问题：长文档处理要么堆原生窗口（贵、过长仍衰减），要么外挂压缩/手写 harness（策略写死）。模型若已能写大仓代码，能否在「几乎无先验」的工具面上被训成自己管理上下文——读切片、派生子 Agent——而不是靠人类脚手架硬编码分解路径？
   - 机制/设计：极简 harness 仅两工具：`read_chunk(start,end)` 读文档 token 区间；`spawn_subagent(subtask)` 以新鲜上下文克隆自身，返回子 Agent 的 `\boxed{}`。对 Qwen3.6-35B-A3B 做合成 oracle SFT，内化三类分解：tree reduce（顺序无关聚合/检索）、sequential fold（顺序依赖累加器）、边界续读（条目跨块时追加 200 token）。推理时每 Agent 限 8K 上下文；不硬编码树深或提示模板。尝试过 SFT 后 RL，但高方差且塌到更弱策略，故主结果为 SFT。
   - 证据：与 GPT-5.4（满文档、至 1M）及基座 Qwen（满文档、Tinker 64K 帽）对照。RULER（13 任务×长度）：微调在 10K–320K 均 ≥0.858（10K 0.949），低于 GPT-5.4 的 ~0.93–0.95 但仍可用；CWE 随长度从 1.00 降至 0.18（有损聚合策略）。OOLONG-synth：文档 >40K 时微调逼近/追上 GPT-5.4（40K：0.535 vs 0.600；80K：0.561 vs 0.539；320K：0.470 vs 0.479），而基座在 40K 已掉到 0.388 且无法评更长。复杂度对文档长 \(n\) 为 \(O(n)\)（相对稠密注意力 \(\Omega(n^2)\)）；tree reduce 可并行。
   - 局限：结论自承不宣称充分泛化；训练文档 ≤14K，160K+ 出现分布错配；无独立 Limitations 节。评测样本偏小（RULER 每类型 5 题、OOLONG 每家族 10 题）；未系统对更多前沿满上下文模型；RL 阶段失败。失败条件：在常识词频类任务上沿用有损聚合却不改 leaf 统计；或把「8K 子 Agent」当已替代企业长附件流水线却未扩训练分布/加恢复型 RL。
   - 对办公 Agent 或 Agent 基础设施的意义：把 context engineering 从「运行时外挂压缩模块」推进到「策略内学会何时读、如何切、如何合并」——适合超长附件/纪要/政策包。生产可对标：每调用硬预算（如 8K）+ 可审计的 range 读与子任务委托，并与记忆层（原文外置）叠加，而不是只加更大上下文窗口。

1. **["Ask the User to Approve" Is Not a Security Control](https://www.darinor.com/blog/human-in-the-loop-is-not-a-control)**
   - 元信息：2026-10-03；已发布（Darinor 一手工程博客）；主题标签：办公 Agent 人机审批 / 审批疲劳 / Deny-by-construction·Allow-by-policy·Ask-with-context / 审批率与金丝雀度量 / 审计；分级：A
   - 核心问题：多数 Agent 产品把「弹窗让人点 Allow」写成安全控制；但人在第三天起会把近乎相同的请求当成反射，拒绝成本又高于放行——确认框何时退化成「带按钮的日志事件」，以及人的注意力应花在哪一类判断上。
   - 机制/设计：把人类审阅当稀缺预算，按顺序拆三层。(1) **Deny by construction**：永远不该做的事（出站白名单外、读凭证文件、工作树外写）不进提示框，由运行时/schema/策略直接拒；(2) **Allow by policy**：低影响、可逆、窄委托身份下的动作免审，把队列腾给真正决策；(3) **Ask, with context**：外发数据、部署、删除、花钱、授权限等才问人——提示写清**效果**而非命令串、展示读过的不可信内容溯源、默认拒绝且单次作用、禁止危险档「always allow」、同会话高档审批过多视为设计债。度量：按提示类型的批准率（≈99% 应收编进策略）、决策时延（亚秒多为橡皮图章）、测试环境注入明显恶意金丝雀、统计 standing grant 真实策略面。
   - 证据：全文给出疲劳四因（基率 / 隐藏注入上下文 / 激励偏向 yes / 攻击者可塑形请求）与三层合同；明确「审批轨迹须含人看到的上下文」，事故调查从「用户点了 Allow」开始而非结束。
   - 局限：偏通用 Agent 安全论述，无邮件/日历连接器实现或线上误批率；金丝雀与批准率阈值需自建。失败条件：只加更多确认框却不把高频无害动作收进策略；或危险档仍开「always allow」。
   - 对办公 Agent 或 Agent 基础设施的意义：发信、改日程、删共享表前的 HITL 必须先削队列再问人——把读选区/草稿当策略放行，把外发与不可逆写钉成效果可读、默拒、可度量的稀缺审批。生产可把「批准率 / 决策时延 / 金丝雀漏批」做成审批 harness 回归门，并与 Gatekeeper 异步批审或草稿+人审车道对齐。

2. **[Cloudflare OS simulates approvals, but never for MCP writes](https://akillness.github.io/posts/cloudflare-os-mcp-approvals-still-wait/)**（底层：[gatekeeper-mcp README](https://github.com/cloudflare/cloudflare-os/blob/5cae880e5e54563895a067e7f4dae67514e581be/packages/gatekeeper-mcp/README.md)、[`mcp-shared/src/session.ts`](https://github.com/cloudflare/cloudflare-os/blob/5cae880e5e54563895a067e7f4dae67514e581be/packages/mcp-shared/src/session.ts)、[`mcp-shared/src/tools.ts`](https://github.com/cloudflare/cloudflare-os/blob/5cae880e5e54563895a067e7f4dae67514e581be/packages/mcp-shared/src/tools.ts)）

   - 机制/设计：审计与源码一致——模拟是**按 Gatekeeper 手写 overlay** 的合同，不是平台默认：Google 有 `gmail-overlay.ts`，Notion/GitHub/Home Assistant 各有仿真；`delivery: "continue-with-simulation"` 把待批动作记入 Durable Object 上的 action journal，读路径按 action-id 回放 pending 世界。MCP 路径在 `session.ts` 对非读工具固定 `awaitDecision: true` + `implementsRevert: false`——因 MCP 无法预测副作用，读面不能假装已写。`tools.ts` 的 `classifyTool`：仅当 `readOnlyHint === true` 才当 observation 立即执行；`byo` 端点写永不可 auto-apply，`vetted` 门户还需 `destructiveHint === false` ∧ `idempotentHint === true` 才 eligible；Overseer 在待决手动决策时挂起 Agent 回合，**拒绝则回合结束**。Gadget 侧则拿 `pending`+`actionId`，不挂起整轮。

   - 对办公 Agent 或 Agent 基础设施的意义：把跨应用办公拆成三条车道——**原生 Gatekeeper 模拟写 / MCP 同步人审写 / 服务器自证只读**——再谈邮件日历连接器。生产应：发信/改表优先原生 Gatekeeper；MCP 写按同步审批编排；接 BYO 前审全部 `readOnlyHint`；关 `MCP_PORTAL_TRUST_ANNOTATIONS`；门户关掉不需要的删改工具。

3. **[MCP Token Passthrough: The Shortcut That Turns Your Server Into a Confused Deputy](https://fullmakt.ai/blog/mcp-token-passthrough-audience-binding)**
   - 元信息：2026-10-05（Fullmakt Team 一手工程博客；对接其 MCP OAuth / 凭证代理实践）；已发布；主题标签：Agent 系统集成 / MCP 禁止 token passthrough / RFC 8707 audience·RFC 9728 PRM / 凭证隔离与按次审计 / 会议纪要→财务 API 失败案例；分级：A
   - 核心问题：办公 MCP 常把入站 `Authorization` 原样转发给 CRM/工单/支付 API——握手图上看似有 OAuth，实则破坏 audience 绑定，把服务器变成 confused deputy；一次日志泄露或注入工具响应可让同一令牌打穿整条下游链，且审计只能看到「用户 X」，看不到「哪个 Agent 经哪台 MCP」。
   - 机制/设计：正确流是两跳两凭证——客户端为 MCP 拿 token，MCP 校验后再用**独立下游凭证**出站。修复合同：(1) 入站严格校验 `aud`（规范化比较）；(2) authorize/token 请求带 RFC 8707 `resource`，issuer 拒绝 resource 不一致的 code 交换；(3) PKCE S256；(4) 下游用 RFC 8693 token exchange 或服务端凭证代理，短时任务范围；(5) Agent token 用错表面直接拒（文中 `403 wrong_token_surface`）；(6) 在动作边界记 Agent、工具、目标、结果，**永不记 token**。Fullmakt MCP：authorization-code+PKCE、RFC 9728 资源元数据、resource 必须点名本端点；上游 secret 仅在调用时服务端解析并过策略，模型不可见。
   - 证据：文内「会议纪要 MCP + passthrough 财务 API」失败链——投毒日历邀请→工具打日志含 header→工单粘贴→宽 scope 一小时 token 直接打财务；对照清单：搜出站是否复制入站 Authorization、解码 `aud`、grep bearer、确认下游审计是否点名 Agent、缩短 lifetime。另链其 [MCP+OAuth 博文](https://fullmakt.ai/blog/mcp-oauth-for-ai-agents) 的 broker 四职（策略 / 凭证注入 / 审计 / 吊销）。
   - 局限：产品团队立场，未公开第三方 MCP 误配普查；自承无法修正你自建且仍转发 token 的服务器。失败条件：只给 Agent 办 OAuth 却让 MCP 透传同一 Bearer；或审计只记人类主体。
   - 对办公 Agent 或 Agent 基础设施的意义：邮件/日历/CRM 集成的权限边界在**凭证受众**，不在「有没有登录框」。生产验收：「入站 token 不得出现在出站头」「下游审计能答哪个 Agent」「泄露一枚 token 不得通吃财务+邮箱」——与 Cloudflare Gatekeeper 持证、Airlock 预览不回灌 Agent 同一条隔离轴。
