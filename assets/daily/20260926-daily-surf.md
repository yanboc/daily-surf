1. **[Scope Before You Persist: Preventing Cross-Family Interference in Agent Memory](https://arxiv.org/abs/2609.29144)**
   - 元信息：2026-09-24（arxiv abs；v1 submitted 2026-09-24）；预印本；主题标签：Agent Memory / 持久技能编辑 / 认证范围–检索范围对齐 / 跨家族干扰 / ORC 门闸；分级：S
   - 核心问题：冻结权重下的持久记忆（改 prompt/skill）可把局部反馈写成长期态，但「本家族证据可认证」≠「全局部署安全」——一条对某任务族正确的技能，经单一全局记忆检索后会伤害无关家族。需要同时回答是否该写入，以及写入后应在何处被取回。
   - 机制/设计：ProcStream-RSI（12 轮代码修复流、9 个可复现任务族）上比较全局 vs 家族作用域记忆。ORC（Orthogonal Regression Control）门闸：在同批 probe 上对 public/private/metamorphic 三通道做单侧 bootstrap 下界（\(\delta_{\mathrm{new}}=0,\delta_{\mathrm{reg}}=0.02\)），并要求历史族无回归后才接受 360 字符技能提案。Scoped-ORC 不改提案与门闸，只把已接受技能写入来源族槽位，检索时 \(K_t(f)\) 仅对本族返回该槽，否则回退初始技能；对照 Global-ORC 用同一紧凑全局技能覆盖所有族。
   - 证据：固定提案/决策干预（8 流）：Scoped 均值轨迹效用 0.816 vs Global 0.713 vs Static 0.775；同 8 次接受在 Scoped 有害部署 0、Global 6。27 流全长随机序：Scoped−Global 轨迹效用 +0.063 [0.037, 0.094]；接受 63 vs 12，多接受流 19/27 vs 2/27；有害/接受 0/63 vs 6/12。机制例：边界族隐式效用平均 +0.398，同时拖累 missing/rotation 等族 −0.461/−0.234 等。门闸内 public/private AUROC 约 0.752/0.998，但局部安全接受仍可伤全局——说明需范围匹配。
   - 局限：Limitations——仅九个代码契约族、单一冻结模型与可检查脚手架编辑；尚缺 compounding 的 cumulative one-shot 对照、开放世界/错槽路由、更多 editor 骨干与自动学到的不变量。失败条件：把局部认证技能写进全局记忆并无作用域检索；或路由错族时退回初始策略不足。
   - 对办公 Agent 或 Agent 基础设施的意义：企业知识工作里「合同条款 / 报销规则 / 某业务线话术」本就应按租户或流程族分槽——认证证据来自哪一族，检索就只对该族生效；可直接映射为按工作区/应用/客户分区的技能记忆，避免一条本地修复污染其他办公流程。

2. **[When Can Agents Forget Their Reasoning? ICLR for Long-Horizon Agent Context Compression](https://arxiv.org/abs/2609.29875)**
   - 元信息：2026-09-24（arxiv abs；v1 submitted 2026-09-24）；预印本；主题标签：Context Engineering / 在线推理压缩 / 代理熵排序 / 状态外置可遗忘性 / WorkBuddyBench（含 Office）；分级：S
   - 核心问题：长程 Agent 不断堆积 reasoning，即便行动与观测已落地，上下文仍膨胀。与静态 CoT 压缩不同，删掉历史推理会改变后续行动与整条轨迹；需要弄清「何时可安全遗忘推理」，而不是只压短一次生成。
   - 机制/设计：ICLR（Interaction Aware Compression for Long Horizon Reasoning），无训练、在线写回。(1) 交互步 \(S_t=(R_t,A_t,O_{t+1})\)，只压缩刚完成步的 reasoning，动作/工具调用/观测/终答原样保留；(2) 按双换行切块，冻结 Qwen3.5-9B 在全史条件下算块均代理熵，删最低熵 \(\rho=0.8\) 比例块并替换为 `[SKIP]`（\(N=1\) 不删）；(3) scorer 超 42K 则跳过该步压缩，不截断行动模型上下文。辅以未来必要性探针、激活修补与「代码/文件/工具输出/环境反馈」外置态分析。
   - 证据：WorkBuddyBench Full260（DeepSeek-V4-Flash）：均值 reward \(0.699\to0.718\)，input/output/cache-read 分别约 −25.5%/−14.4%/−33.3%；W/T/L=102/76/82。Appendix E：Security \(0.478\to0.707\)（+22.9pp）主导增益；Office \(0.818\to0.776\)、Code/Web 略降。Pilot40 上 Avg 70.3 vs 多类摘要/窗/PACE 等。80 题消融：ICLR 0.738 vs Base 0.627；全删 thinking 0.718、Step-only 0.711，随机删均不及全史熵排序。轨迹放大：删 10% reasoning token 可致总 input −60.5%，删 20% 仅 −44.0%。外置态：未外置时未来行为风险 67.3% vs 已外置 36.2%；写盘后清 reasoning 规则分不变（0.759）。
   - 局限：正文无独立 Limitations；Full260 上 Code/Office/Web 域分下降且 Code input 反增；固定 \(\rho=0.8\)、依赖换行切块与跨模型代理熵；scorer 触顶即跳过压缩。失败条件：关键结论仍仅存在于 reasoning、尚未写入文件/工具结果时过早删块；或局部删除经工具选择放大成更长轨迹。
   - 对办公 Agent 或 Agent 基础设施的意义：给「改文档/跑脚本/读报错」类办公轨迹一条默认 compaction——优先砍低熵自言自语，保工具 I/O 与外置产物；生产上可把「决议是否已写入纪要/表格」当作可遗忘闸，而不是无差别摘要整段对话。

3. **[DocuTeam: Mixed-Initiative Multi-Agent Discussions around Evolving Documents](https://arxiv.org/abs/2609.29309)**
   - 元信息：2026-09-24（arxiv abs；v1 submitted 2026-09-24）；预印本；主题标签：Multi-Agent / 混合主动讨论 / 文档锚定协同 / 办公知识工作 / 人机编排；分级：S
   - 核心问题：开放式知识工作（写计划/报告）常靠多人讨论打磨共享文档，但现有多 Agent 要么只做「用户中枢」的主动反馈，要么要用户自己发起并全程编排 agent 间讨论；缺少「用户与多 Agent 都能就演进中的文档主动开聊、互驳、再写回」的混合主动形态。
   - 机制/设计：Notion Chrome 扩展 + FastAPI。(1) 文档块锚定讨论气泡 + 侧栏线程；模式 Idea/Discussion/Evaluation。(2) 引擎循环：意图抽取 → moderator 决定下一发言/问用户/结束 → 指定 agent 做 Issue/Claim/Support/Rebut/Question → 异步更新各 agent 长期记忆与摘要。(3) Agent 主动：编辑块 2s debounce 后，≥3 名相关 agent 对三模式打 0–1 分，任一模平均 >0.75 则自动开讨论；用户可加踢 agent、直接插话，agent 也可红框气泡索要偏好。生成用 gpt-5-mini，其余管线 gpt-4o-mini。
   - 证据：Within-subjects N=20，两任务活动策划；对照为同引擎但无 in-situ/无 agent 主动的侧栏基线。盲评：Novelty 3.20 vs 2.68（p=0.047）、Relevance 3.30 vs 2.78（p=0.048）、Specificity 3.25 vs 2.28（p=0.001）；Workability 无显著差异。过程：steering 消息 2.70 vs 5.00（−46%）、文档改词 448.7 vs 323.0、应用讨论消息 12.3 vs 9.0；用户发起更偏 Discussion 而非 Idea。NASA-TLX 总分无显著升高（4.65 vs 4.26）。
   - 局限：Limitations——仅活动策划场景、约两小时短会话，未验证写作/视觉设计等工作流与长期策略演化；未独立评测对话引擎自然度/有用性（两条件共用同一引擎）。失败条件：多气泡并发时信息过载；或阈值/模式阈值触发过多干扰写作。
   - 对办公 Agent 或 Agent 基础设施的意义：把「多角色评审合同/方案」从聊天编排改成文档中介闭环——讨论钉块、主动跟改、摘要降监控成本、可选写回；生产上可把 proactivity 阈值与租户角色配置成可审计策略，而不是让用户当多 Agent 调度员。
